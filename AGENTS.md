# Artmate WMS — правила разработки

## Рабочий процесс

Пользователь поручил автономно реализовать первую интерактивную версию и разрешил агентов. Продолжать небольшими проверяемыми этапами; записывать принятые решения. После каждого завершённого и проверенного этапа делать локальный Git-коммит: пользователь явно разрешил регулярные коммиты. Публикацию и push выполнять только по отдельному запросу. Использовать Conventional Commits на английском; не включать базу, резервные копии, секреты и результаты сборки. Swagger/OpenAPI и клиент Orval воспроизводятся генерацией и не хранятся в Git.

## Архитектура

- Yarn Classic workspaces + Turborepo; apps/web — Next.js App Router; apps/api — NestJS.
- Источник API — NestJS DTO и Swagger/OpenAPI. Web получает типы и клиент генерацией Orval; generated-файлы не редактировать.
- FSD: app/ — привязка маршрутов; src/_app — providers; src/_pages — композиция; src/features — сценарии; src/entities — чтение; src/shared — UI/инфраструктура; src/widgets — общие крупные блоки.
- Импорты идут вниз по слоям. Между слайсами использовать публичные index.ts.
- Серверная логика и проверки остатков только в API. localStorage не является источником складского учёта.
- Формы — React Hook Form + Zod; мапперы формы в feature/lib, мутации в feature/model.
- UI-state находится в feature/lib; read hooks — entities/model; транспорт и generated API — shared/api.
- Связанные утилитарные операции можно оформлять статическим классом; Nest providers сохраняют instance DI. Приватные методы именовать с начальным _. 

## Правила склада

Входящие паллеты и паллеты хранения готовой продукции содержат один SKU. Исключение: общая накопительная паллета в зоне сборки содержит готовые короба разных тематик. Оттуда добровольно берутся второстепенные задания на размещение отдельных коробов по тематическим паллетам хранения; до размещения они недоступны для отгрузки. Короб в пути остаётся на балансе. Приёмка до подтверждённого размещения не пополняет баланс и недоступна для сборки. Каждая паллета приходуется отдельно по скану паллеты и адреса; полностью размещённая приёмка автоматически уходит в архив. FIFO по фактическому поступлению. Смешение партий одной тематики допускается при нехватке старой; состав коробов сохраняется. Внутри партии время сборки — мягкий приоритет. Объём отгрузки независим от сборки. Задания можно брать из свободной очереди или назначать из интерфейса; исполнитель каждой команды проверяется сервером. Короб подтверждается сканом до сканов товара, последний скан атомарно закрывает короб в зоне сборки. Каждый новый короб — отдельное задание. Закрытие короба освобождает сотрудника, а следующее задание он берёт явной командой. При упаковке количество сохраняется; отгрузка списывает только выбранные короба один раз.

Редактирование схемы: перенос помещения или коридора атомарно сдвигает активные стеллажи, отдельные места и проходы, целиком расположенные в исходном участке. Все адреса ярусов активной секции (включая архивные) следуют ей один раз. Архивные отдельные объекты не входят в группу. IDs, QR, остатки и адресные ссылки товара сохраняются. Состав группы определяется до изменения геометрии, после переноса группа обязана поместиться в том же участке; любой конфликт откатывает всю команду. Это изменение схемы, без физического задания на перемещение паллеты.

Изменение размеров участка — отдельная операция resizeSpace: меняются только границы, включая X/Y при растягивании с северной/западной стороны; оборудование не сдвигается. Исходное содержимое обязано оставаться в том же участке. Перемещение updateSpace сохраняет групповой перенос. Масштаб колеса/трекпада — только viewport, без записи складских данных. Рабочее поле расширяется отдельно от реальных помещений.

Копирование секции — отдельная атомарная команда copyRackSection: новые ID, QR и автоматически назначенные коды/названия секции и активных ярусов. Сохраняются размеры, поворот и настройки адресов, включая ручную блокировку; товары, резервы и архивные ярусы не дублируются. Предварительное размещение на карте не записывает складские данные. Автозаполнение новых мест учитывает все адреса и секции, включая архивные, и не переименовывает существующие.

Количественный учёт: signed-позиции журнала сохраняются в отдельной append-only таблице той же транзакцией, что состояние и cached response команды. История не входит в WorkspaceDto. Schema8 фиксирует один начальный остаток, не переписывая старые команды и документы. Внутренние операции сохраняют количество каждой партии; сверка сравнивает позиции целиком. Корректировки сырья требуют исходного количества и адреса, работающего сотрудника и причины; резервы/движения защищены. Списание сохраняет короб как written_off с исходным составом, исключая его из баланса и отбора. Исторический факт приёмки не переопределяется пересчётом. Автор нового HTTP-события берётся из серверной сессии; отсутствующий автор старого события не выдумывается.

## Вход и права

Schema9 добавляет отдельные auth_accounts/auth_sessions/auth_events/auth_login_limits. Миграция не создаёт аккаунт и не переписывает старый склад, журнал, revision или cached responses. Первый руководитель создаётся через UI со своим паролем; общего пароля нет. Password scrypt, cookie HttpOnly/SameSiteStrict, CSRF в памяти web, роли manager/employee. Все складские HTTP endpoints защищены, права и владельцы перепроверяются внутри SQL lock до replay и мутации. Доверенные прямые domain unit tests не означают HTTP bypass. Пароли и сырой session token не попадают в WorkspaceDto, журнал или commands.

Назначение employeeId другого исполнителя допускается при планировании руководителем. Фактические сканы/take/place выполняет назначенный вошедший сотрудник. Автор ledger/activity берётся из сессии. Worker получает проекцию Workspace: себя, свои/свободные задания и активные приёмки, без управленческой истории/отгрузок. Анонимные addressHolds сообщают занятые резервом адреса без чужих сотрудников и заданий; placement-options всегда считаются по полному state. При смене личности/прав/сессии очищается querycache и replay registry; проверки auth epoch охватывают transport и все продолжения складской команды, включая fallback.

## Смены и выработка

Schema10 добавляет employee_shifts, shift_intervals и append-only work_events отдельно от WorkspaceDto. Смена и факты работы записываются той же SQL-транзакцией, что складская команда и её cached response. Replay и откат не дублируют результат. work_tracking_since фиксируется один раз; миграция не меняет прежние 15 таблиц, revision, auth, ledger и commands. Уже работающие/отдыхающие сотрудники получают observed_from_migration от момента включения истории, без прошлого времени и выработки.

Выработка — только фактическое закрытие короба и units внутри него, размещение входящей паллеты, размещение готового короба и завершение перемещения паллеты. Скан, захват, назначение, отмена, корректировка и отгрузка не создают новые результаты. Событие не исчезает после списания товара. HTTP-исполнитель из сессии; изменение чужой смены сохраняет субъекта и автора раздельно.

Report/history ограничены правами; employee только self, manager может фильтровать. Период — включительные календарные даты Europe/Moscow, SQL UTC-полуинтервал, максимум 366 дней. Время смены/перерывов обрезается по периоду и now; currentShift/currentJobs показывают актуальное состояние независимо от периода. Время working не называется активной работой. Старые boxesToday/unitsToday остаются накопительными и не используются как сегодняшний отчёт. Break/end запрещены с коробом или паллетой в пути; сборка ставится на паузу, её резервы сохраняются.

## Инвентаризация

Schema11 добавляет документы инвентаризации, отдельные ответы их команд и монотонные версии ячеек. Исходные складские таблицы, auth/workforce/ledger, revision и прежние commands при миграции не меняются. История не входит в WorkspaceDto. В scope только активные rack/floor адреса до 200; зоны сборки/отбора/приёмки/отгрузки не объявляются пересчитанными выбором помещения.

Подсчёт не меняет остатки. Raw quantity относится к известной паллете/партии; finished считаются по стабильным кодам коробов, неизвестные коды блокируют approval. Для raw presence=false строка не наблюдалась на данном адресе, presence=true quantity 0 — пустая физическая паллета. Известный товар переносится только между пересчитанными адресами документа с сохранением идентичности/партии/FIFO. Отсутствующий короб не удаляется, а списывается как written_off с исходным составом; пустые паллеты не вывозятся автоматически.

Manager approval с причиной атомарно сохраняет все исправления, количественный ledger(kind=adjustment, referenceType=stocktake), состояние документа и cached response. Старый requestId не выполняет изменения повторно, свежие права проверяются до replay. Пересчёт/утверждение не создают факты выработки. Scope/ownership и working-смена проверяются сервером; автор из сессии, approved history не пересчитывается по будущим остаткам.

Версии ячеек учитывают физику и резервы под общей SQL-блокировкой. Out-and-back и reserve-release не оживляют старые counts; explicit refresh сбрасывает только одну строку и сохраняет прошлый счёт в истории. Любая stale/busy/unknown строка блокирует атомарное approval. expectedRevision защищает вкладки. Web сохраняет dirty input при polling, не понижает revision при replay и не кэширует ответ прежней auth epoch. StocktakeDto подтверждается отдельным responseguard в replay transport; warehouse command по-прежнему требует Workspace.

## Визуальное направление

Тёмный графит, один мятно-зелёный акцент, стеклянные поверхности и тонкие световые границы. Читаемость и рабочие действия важнее эффектов. Русские тексты, понятные статусы, клавиатурный фокус и reduced motion обязательны.

## Проверка

После изменения API: yarn api:generate. Перед сдачей: yarn check-types, yarn lint, yarn test, yarn build и браузерная проверка основных действий. Не выдавать локальный прототип за промышленно готовую WMS. Не менять соседний artmate-monorepo и не использовать его секреты.

## Рабочее место сотрудника

`/work` — отдельная компактная композиция widgets/employee-workspace. Features employee-assembly, employee-handling, employee-workday и compact stocktakes не импортируют друг друга. Руководитель сохраняет прежние экраны. Shared EmployeeScan отвечает за ввод/Enter и последовательную очередь только одного auth/operation/box контекста, без складской бизнес-логики. Идентичные товарные штрихкоды не дедуплицируются. Ошибка сохраняет и останавливает очередь до исправления; ответ API является единственным подтверждением учёта. Неотправленные сканы не переносятся в следующий короб. Не обещать offline или аппаратную проверку без оборудования.

Начало задания — явная команда; effect не выполняет claim/pack/place. Физический перенос приоритетнее другой работы. Общий provider активности защищает уход, паузу и завершение смены при очереди сканов и dirty-подсчёте. Внешнее изменение задания/смены или ошибка polling не размонтирует dirty-форму; ввод остаётся до сохранения/явного отказа, серверные проверки прав/revision продолжают действовать.

## QR рабочих зон

Рабочий экран удерживает Screen Wake Lock только для собственной working-смены и видимой страницы; освобождает при перерыве/выходе, поздний sentinel старой сессии не удерживается. AudioContext один на рабочий экран, активируется жестом. Звук только по результату onScan/gateway, не enqueue: pass молчит, handled/accepted — успех, blocked/failed — ошибка. Смена формы после успешного последнего скана не теряет подтверждение; прежний auth epoch молчит. Звуки/удержание не обходят ограничения iOS и не меняют складские команды. См. ADR083.

Постоянные таблички зон и адресов печатаются через `/labels/a4`: четыре на А4, выбор по `{type,id}`, QR только из существующего getLabel. Named page `warehouseSigns` независима от рулонных `wmsRoll75`/`wmsRoll100`. Адреса одиночно и комплектом по умолчанию печатаются горизонтально 120×75 через общий LocationRollLabel: QR слева, номер места/ярус справа, адрес внизу; номер берётся из явного сегмента имени, без modulo по коду. Для произвольных имён сохраняется полный адрес, архив помечается. А4 и прежние форматы сохранены; короба, паллеты и приёмки по умолчанию остаются 75×120. Рабочие зоны по умолчанию также120×75: только QR слева и «Рабочая зона: назначение» справа; общий WorkZoneRollLabel для одиночной/массовой печати, без бренда/кода/payload/повтора имени. Корневой контейнер печати получает named page выбранного формата. См. ADR085 и ADR054. Печать блокируется до загрузки полного набора QR и при недоступности выбранных объектов; native Ctrl+P не должен выдавать частичный комплект. Не смешивать рабочую зону и физический адрес, не создавать новые идентификаторы ради повторной печати. См. ADR 053.

Schema12 меняет только номер схемы; `warehouse.workZones`/`zoneWork` — additive defaults при чтении, старые warehouse JSON, rows и cached commands не переписываются. WorkZone — логическое объединение locationIds, без вместимости и новой геометрии. QR `artmate-wms:work-zone:<id>` отличается от QR адреса; название и код генерируются атомарно с учётом архива. Назначение/архив/состав защищены активной работой. Все сборочные зоны ссылаются на текущий общий накопитель; receiving bindings — площадки приёмки, putaway — источники сборки, shipping — picking/shipping адреса.

startZoneWork атомарно захватывает/возобновляет работу под SQL lock от собственного actor и working-смены; receiving pallet имеет одного исполнителя, в том числе для legacy place. После физических завершений очередь той же зоны продолжается на сервере. Исключение — размещение с общего накопителя: вход и завершение не назначают следующий короб; сотрудник выбирает любой доступный короб сканом. QR не меняет количество. Пустая очередь проверяется явным повторным сканом/кнопкой, не эффектом. leave/переход блокируют carry, WIP и частично подтверждённую отгрузку.

Shipping execution отдельно от manager planning: own employeeId/workZoneId/scannedBoxIds, точный набор зарезервированных готовых коробов, явный finish — единственное списание. Права/сессия/ownership/физика проверяются до replay. Worker projection содержит только свои отгрузки/zoneWork. Shared scan gateway generic; распознавание QR и маршрутизация — в workday/widget. Обычные сканы обходят async preflight синхронно, очередь не теряет burst. Recovery discards только failed unsent queue после явного подтверждения, без отмены запроса или складского факта.


## Запас этикеток коробов

Schema13 добавляет отдельные box_label_batches/preprinted_box_labels/box_label_commands без переписывания складских таблиц, истории или прежних cached commands. Тираж 1–1000 выпускает только идентификаторы, не товар. QR `artmate-wms:box:BOX-PRE-…` привязывается к текущему коробу после подтверждения FIFO-паллеты в той же SQL-транзакции scanTask. Повтор своего текущего QR безопасен, чужая/использованная этикетка не возвращается в свободные даже после отгрузки или списания. Закрытие короба связывает registry.box_id атомарно с остатком, журналом и выработкой; старые автоматически созданные коды работают. Все три command namespaces проверяют конфликты requestId друг с другом; свежие права до replay. Registry не включён в WorkspaceDto, manager-only reads/issuance, печать свободных по100 максимум с полным SVG readiness. См. ADR055.

## Доступ с телефона

После `yarn phone:setup` локальная CA/ключи остаются в игнорируемой `.data/phone-access`, глобальное доверие компьютера не меняется. `yarn start` поднимает HTTPS3443 на конкретных RFC1918 IPv4 и HTTP3442 только для публичной CA/инструкции. API/Web фиксированы на loopback4080/3080. Gateway добавляет Secure к каждому Set-Cookie, удаляет spoofed forwarding headers и сохраняет Origin/CSRF; API принимает только точные origins из стартовой конфигурации. Ошибка LAN не гасит localhost. Не отдавать .key/данные/команды через enrollment HTTP; не включать публичный tunnel или проброс портов. Доверие CA устанавливает пользователь на телефоне. См. ADR056 и docs/PHONE_ACCESS.md.

## Камера сотрудника

Кнопка камеры в Shared EmployeeScan — одноразовый источник строки кода. Динамический локальный ZXing читает QR и товарные EAN/Code128 без зависимости от BarcodeDetector. Результат проходит тот же RHF/Zod, gateway и scan queue, включая исправление остановленного ошибочного скана. Открытие не создаёт учётного события; после одного результата камера закрывается. Новое открытие может принять тот же SKU как новую единицу. При закрытии, фоне, смене auth/operation и позднем getUserMedia все tracks/decoder завершаются, устаревший результат не отправляется. Не подменять аппаратную проверку тестовым видеопотоком.


## Размещение любого короба и общая очередь

В зоне размещения idle-binding jobKind/jobId null означает ожидание скана любого готового короба. UI показывает «Возьмите любой короб» по zone.kind, не «нет работы» и не первое конкретное задание. takeAnyPutawayBox атомарно разрешает полный boxCode/QR, проверяет рабочую зону, доступность и собственную working-смену, освобождает прежнее своё claimed при смене выбора, назначает именно отсканированный короб, резервирует совместимый адрес и переводит in_transit. Чужие claimed и любой переносимый короб защищены. placePutawayBox подтверждается только адресом; источник и удерживаемый короб известны серверу, фиктивные сканы не создаются. После перезагрузки в пути сразу нужен адрес. Старые id-based двух/четырёхскановые команды совместимы через общие переходы. См. ADR058.

/tasks объединяет реальные документы через entities/work-queue, без второй базы задач. Сотрудник видит проекцию своего сервера; неизвестный автор приёмки не объявляется свободным. ## Автоматическая очередь работ

По запросу пользователя прогноз и план остаются чтением, а отдельный WorkAutomationService создаёт свободные задания по актуальному опубликованному плану. Schema18 хранит настройки, происхождение и replay отдельно. SQL lock защищает FIFO и очередь; автоматикой нельзя менять назначенные или начатые задачи. Пакет до 10 коробов к потребности или 1 впрок; неизвестная физическая вместимость/нераспределённые остатки запрещают создавать работу. Scheduler только main, без фоновой работы при DI/Swagger. Размещение создаётся на каждый готовый короб; ≥80% общей паллеты повышает приоритет его очереди. Подтверждение нового короба резервирует один физический слот, полная паллета запрещает новый короб с учётом открытых коробов всех сотрудников. Последний скан и безопасный выбор следующей задачи атомарны. См. ADR080.

## Ограниченная очередь сборки — 2026-10-30

WorkAutomationService поддерживает максимум пять незавершённых сборочных задач,
считая свободные, назначенные, активные, paused и ручные. Ручные/защищённые не
снимаются; claim слот не освобождает, completion позволяет пополнение ближайшим
15-секундным циклом. Один незавершённый auto task на SKU; urgent batch ≤10,
backlog batch=1. Внутри urgent/backlog сначала never-served, затем least recently
served по createdAt происхождения реально взятой/начатой/завершённой партии,
затем актуальный backlogRank и название. Нетронутые свободные и withdrawn не
обновляют recency. Только одна нужная тема может продолжаться партиями.
Лимит пяти задач отделён от двадцати mutations за run; при сокращении старой
очереди не создавать замены до завершения необходимых снятий. FIFO, история
снятий и общий SQL lock сохраняются. См. уточнение ADR080.

## Сборка по одному коробу

Создание из плана резервирует FIFO на один полный короб. Ручной запрос до
пяти коробов атомарно создаёт столько отдельных задач. Для одной тематики
считаются все незавершённые задачи, включая назначенные и на паузе, максимум
пять. Суммарный лимит очереди — 100 незавершённых задач с учётом ручных и
занятых. За проход планировщик меняет не больше двадцати задач. Рекомендация на месяц учитывает объём независимо от буфера.
Внутри приоритета планировщик делает круг по тематикам. При явном взятии сервер
предпочитает давно не запущенные тематики и сохраняет приоритет назначенной
работы и срочной потребности перед сборкой впрок.

После закрытия короба следующий не захватывается. Свободные старые
автоматические пачки сжимаются до одного короба. Если старое автоматическое
задание уже начато, оставшийся резерв освобождается после закрытия текущего
короба, а остаток потребности снова рассчитывается планом. Ранее заведённые
ручные пачки сохраняют объём и историю. Размещение и перемещение уже поштучны
по коробу и паллете соответственно.

## Остатки для плана сборки

Источником готового остатка для плана служат складские короба. Утверждённая
инвентаризация влияет на план через складские записи. Ручные суммы и оценки
из прежней версии хранятся в истории, не прибавляются к коробам и не влияют
на доступность сборки или мест хранения. Старый признак исключения SKU
из плана сохраняется. Формы ручного остатка и галочки полного учёта убраны.
Отгрузочные резервы и проверка места по складскому учёту сохраняются.
Версия сохранённой проекции плана исключает ранее рассчитанные суммы.

Количество в пути для плана поступает только из данных маркетплейсов.
Прежние ручные числа не участвуют в расчёте и не меняют идентификатор
предложения. При неполных данных значение остаётся неизвестным. Ссылки на
поставки ведут к интеграциям. Ноль учитывается по данным площадки и её документов.

## Расходники сборки по адресам

Фактический остаток упаковки хранится в плане склада по адресу и виду. Положительный остаток занимает адрес для размещения и перемещений. Приёмка добавляет штуки, пересчёт заменяет количество с проверкой предыдущего остатка и резерва. Учёт включается руководителем после ввода факта. До включения старый процесс сборки доступен. Включение атомарно резервирует упаковку для очереди и требует завершить начатую сборку раскрасок.

Задание на короб из 20 раскрасок резервирует 20 поштучных коробок и один транспортный короб по адресам. Маркеры используют свой процесс. Фоновая очередь распределяет общие комплекты по существующим приоритетам, освобождая резервы отозванных заданий. Закрытие короба списывает упаковку с закреплённых адресов в той же транзакции. Повтор команды возвращает сохранённый результат.

## Штрихкоды тематик

Сборка принимает основной или вручную добавленный штрихкод тематики. Если код отсутствует в справочнике WMS, проверяются сохранённые карточки включённых подключений той же версии. Требуется однозначная привязка к одной тематике и соответствие «одна единица товара». Ошибка синхронизации сохраняет коды последнего успешного импорта той же версии. Добавленные вручную коды проверяются на конфликты в справочнике и карточках. QR паллет и коробов проходят собственные проверки.

## Отбор коробов для отгрузки

Черновик резервирует конкретные короба по дате поступления партии. Свободный
отбор можно взять на рабочем экране или через QR зоны отгрузки. Черновики прежней
версии без исполнителя переходят на поштучный сценарий при взятии. Уже взятые
задания прежней версии завершаются через их существующий QR зоны.

При скане только короб из резерва снимается с учётной паллеты хранения.
Статус staged сохраняет короб на балансе и в резерве отгрузки. Смена адресной
позиции записывается в журнал как shipment_pick с нулевым итогом по партии.
Сканы сохраняются при паузе и выходе из отбора. Последний скан завершает отбор,
после физической отправки руководитель отдельно списывает все короба документа.
Физические паллеты отправки, их QR, вместимость и раскладка этим сценарием не
учитываются. Обычное перемещение целой паллеты остаётся доступно для спуска.
