# Artmate WMS — правила разработки

## Рабочий процесс

Пользователь поручил автономно реализовать первую интерактивную версию и разрешил агентов. Продолжать небольшими проверяемыми этапами; записывать принятые решения. После каждого завершённого и проверенного этапа делать локальный Git-коммит: пользователь явно разрешил регулярные коммиты. Публикацию и push выполнять только по отдельному запросу. Использовать Conventional Commits на английском; не включать базу, резервные копии, секреты и результаты сборки. Swagger/OpenAPI и клиент Orval воспроизводятся генерацией и не хранятся в Git.

## Архитектура

- Yarn Classic workspaces + Turborepo; apps/web — Next.js App Router; apps/api — NestJS.
- Источник API — NestJS DTO и Swagger/OpenAPI. Web получает типы и клиент генерацией Orval; generated-файлы не редактировать.
- FSD: app/ — привязка маршрутов; src/_app — providers; src/_pages — композиция; src/features — сценарии; src/entities — чтение; src/shared — UI/инфраструктура; src/widgets — общие крупные блоки.
- Импорты идут вниз по слоям. Между слайсами использовать публичные index.ts.
- Серверная логика и проверки остатков только в API. localStorage не является источником складского учёта.
- Формы — React Hook Form + Zod; мапперы формы в feature/lib, мутации в feature/model.
- UI-state находится в feature/lib; read hooks — entities/model; транспорт и generated API — shared/api.
- Связанные утилитарные операции можно оформлять статическим классом; Nest providers сохраняют instance DI. Приватные методы именовать с начальным _. 

## Правила склада

Входящие паллеты и паллеты хранения готовой продукции содержат один SKU. Исключение: общая накопительная паллета в зоне сборки содержит готовые короба разных тематик. Оттуда добровольно берутся второстепенные задания на размещение отдельных коробов по тематическим паллетам хранения; до размещения они недоступны для отгрузки. Короб в пути остаётся на балансе. Приёмка до подтверждённого размещения не пополняет баланс и недоступна для сборки. Каждая паллета приходуется отдельно по скану паллеты и адреса; полностью размещённая приёмка автоматически уходит в архив. FIFO по фактическому поступлению. Смешение партий одной тематики допускается при нехватке старой; состав коробов сохраняется. Внутри партии время сборки — мягкий приоритет. Объём отгрузки независим от сборки. Задания можно брать из свободной очереди или назначать из интерфейса; исполнитель каждой команды проверяется сервером. Короб подтверждается сканом до сканов товара, последний скан атомарно закрывает короб в зоне сборки. После последнего короба автоматически берётся следующее доступное задание этому сотруднику. При упаковке количество сохраняется; отгрузка списывает только выбранные короба один раз.

Редактирование схемы: перенос помещения или коридора атомарно сдвигает активные стеллажи, отдельные места и проходы, целиком расположенные в исходном участке. Все адреса ярусов активной секции (включая архивные) следуют ей один раз. Архивные отдельные объекты не входят в группу. IDs, QR, остатки и адресные ссылки товара сохраняются. Состав группы определяется до изменения геометрии, после переноса группа обязана поместиться в том же участке; любой конфликт откатывает всю команду. Это изменение схемы, без физического задания на перемещение паллеты.

Изменение размеров участка — отдельная операция resizeSpace: меняются только границы, включая X/Y при растягивании с северной/западной стороны; оборудование не сдвигается. Исходное содержимое обязано оставаться в том же участке. Перемещение updateSpace сохраняет групповой перенос. Масштаб колеса/трекпада — только viewport, без записи складских данных. Рабочее поле расширяется отдельно от реальных помещений.

Копирование секции — отдельная атомарная команда copyRackSection: новые ID, QR и автоматически назначенные коды/названия секции и активных ярусов. Сохраняются размеры, поворот и настройки адресов, включая ручную блокировку; товары, резервы и архивные ярусы не дублируются. Предварительное размещение на карте не записывает складские данные. Автозаполнение новых мест учитывает все адреса и секции, включая архивные, и не переименовывает существующие.

Количественный учёт: signed-позиции журнала сохраняются в отдельной append-only таблице той же транзакцией, что состояние и cached response команды. История не входит в WorkspaceDto. Schema8 фиксирует один начальный остаток, не переписывая старые команды и документы. Внутренние операции сохраняют количество каждой партии; сверка сравнивает позиции целиком. Корректировки сырья требуют исходного количества и адреса, работающего сотрудника и причины; резервы/движения защищены. Списание сохраняет короб как written_off с исходным составом, исключая его из баланса и отбора. Исторический факт приёмки не переопределяется пересчётом. Автор нового HTTP-события берётся из серверной сессии; отсутствующий автор старого события не выдумывается.

## Вход и права

Schema9 добавляет отдельные auth_accounts/auth_sessions/auth_events/auth_login_limits. Миграция не создаёт аккаунт и не переписывает старый склад, журнал, revision или cached responses. Первый руководитель создаётся через UI со своим паролем; общего пароля нет. Password scrypt, cookie HttpOnly/SameSiteStrict, CSRF в памяти web, роли manager/employee. Все складские HTTP endpoints защищены, права и владельцы перепроверяются внутри SQL lock до replay и мутации. Доверенные прямые domain unit tests не означают HTTP bypass. Пароли и сырой session token не попадают в WorkspaceDto, журнал или commands.

Назначение employeeId другого исполнителя допускается при планировании руководителем. Фактические сканы/take/place выполняет назначенный вошедший сотрудник. Автор ledger/activity берётся из сессии. Worker получает проекцию Workspace: себя, свои/свободные задания и активные приёмки, без управленческой истории/отгрузок. Анонимные addressHolds сообщают занятые резервом адреса без чужих сотрудников и заданий; placement-options всегда считаются по полному state. При смене личности/прав/сессии очищается querycache и replay registry; проверки auth epoch охватывают transport и все продолжения складской команды, включая fallback.

## Визуальное направление

Тёмный графит, один мятно-зелёный акцент, стеклянные поверхности и тонкие световые границы. Читаемость и рабочие действия важнее эффектов. Русские тексты, понятные статусы, клавиатурный фокус и reduced motion обязательны.

## Проверка

После изменения API: yarn api:generate. Перед сдачей: yarn check-types, yarn lint, yarn test, yarn build и браузерная проверка основных действий. Не выдавать локальный прототип за промышленно готовую WMS. Не менять соседний artmate-monorepo и не использовать его секреты.
