# Подготовка и первый релиз WMS

WMS выпускается отдельно от Artmate-monorepo: свои образы, PostgreSQL, том,
конфигурация и master-key. Общими могут быть только сервер и внешний Caddy.
Для WMS выбран отдельный VPS; DNS и первый rollout выполняются отдельно.
Эти файлы не подключаются к серверу автоматически и не меняют инфраструктуру Artmate.

## Что готово в репозитории

- `Dockerfile`: targets `api` и `web`, Yarn frozen lockfile, генерация
  Swagger → Orval внутри сборки. В API весь compiled `dist`, включая ML worker;
  в Web standalone Next. Оба процесса работают от непривилегированного `node`.
- `infra/compose.yml`: отдельный PostgreSQL17, одноразовые миграции, один API
  с планировщиками, Web; наружу не опубликован ни один порт.
- `infra/compose.edge.yml`: собственный Caddy и HTTPS для отдельного сервера.
- `infra/compose.artmate.yml`: только Web подключается к существующей сети прокси.
- `.github/workflows/ci.yml`: типы, архитектура, тесты, build и реальный smoke
  контейнеров с восстановлением backup. `publish.yml` запускается вручную после
  этих проверок и выпускает SHA-теги и digest manifest, без `latest` и без deployment.
  `deploy.yml` — отдельный ручной rollout по проверенному manifest с закреплённым
  SSH host key: [настройка GitHub и VPS](GITHUB_DEPLOYMENT.md).
- Скрипты настройки, preflight, deploy, backup и restore:
  [эксплуатационные команды](RELEASE_OPERATIONS.md).

## Сборка и проверка без production-данных

Нужны Docker Engine/Compose2 с поддержкой `up --wait`, BuildKit и Node24 для
эксплуатационных CLI. На рабочем компьютере исходники могут по-прежнему
запускаться привычным локальным способом. Dev `docker-compose.yml` не заменён.

```bash
docker build --target api -t artmate-wms-api:local .
docker build --target web -t artmate-wms-web:local .
node scripts/container-smoke.mjs
```

Smoke сам создаёт уникальный project, новую БД и временные секреты, публикует
только случайный loopback-порт. Проверяет пустой production, повтор миграций,
вход, Origin/CSRF-границу, Secure cookie, Web/API proxy, compiled ML worker,
backup/restore и чистую остановку. Удаляет только созданные им временные тома.
Не передавать ему конфигурацию живого склада. CI проверяет linux/amd64;
публикация готовит linux/amd64 и linux/arm64.

Домены и ключи не являются build args. Next компилирует внутренний адрес
`http://artmate-wms-api-internal:4080` — одинаковый для обоих вариантов Compose; публичный браузер
обращается к `/api` своего HTTPS-домена. Не менять alias `artmate-wms-api-internal` без пересборки.

## Выбор площадки

### На том же сервере, что Artmate

Рабочий кандидат — `wms.artmate.ru`. До подтверждения не создавать DNS и не
редактировать соседний проект. Проверить реальную свободную RAM/CPU/диск, объём
истории БД, нагрузку Artmate и время ML расчёта. Лимиты в Compose — начальные
ограничения, а не доказательство того, что существующему VPS хватит ресурсов.

1. Отдельный каталог `/opt/artmate-wms`, отдельный Compose project `artmate-wms`.
2. Уточнить настоящее имя сети Caddy, для reference оно `artmate_default`.
3. Использовать `--ingress artmate`, `WMS_PROXY_NETWORK` в защищённом env.
4. По согласованию добавить site block из
   `infra/caddy/artmate-wms.caddy.example` в действующий Caddyfile, проверить
   `caddy validate`, затем reload. БД/API в external-сеть не подключать.
5. Не запускать `compose.edge.yml` и второй слушатель 80/443.

Важное отличие: общий Artmate snippet запрещает камеру. WMS site block использует
`Permissions-Policy camera=(self)` — без этого телефон не сможет сканировать
камерой. WMS cookie host-only `__Host-wms_session`, отдельная от Artmate; общего
логина между проектами нет.

### Отдельный сервер

Выбрать точный домен, настроить A/AAAA на выбранный хост, открыть80/443 и
использовать `--ingress edge`. Caddy получает и обновляет сертификат, хранит его
в собственных томах. PG/API не получают публичных портов. Для телефона достаточно
обычного доверенного HTTPS, складской локальный CA/3442/3443 сюда не переносится.

## Последовательность первого релиза

1. **Проверенная версия.** Выбрать Git commit и пару API/Web образов этого commit;
   предпочтительно зафиксировать registry digests. Настроить GitHub repository,
   права GHCR и защищённое environment `release`. Сейчас push/публикация не делались.
2. **Конфигурация.** Для переноса запустить `init.mjs --existing-key-file ...` с
   исходным ключом WMS; для действительно нового склада — `--new-install`.
   Пароли/ключи Artmate не использовать. Env600, backup-каталог700, preflight.
3. **Пробный перенос.** Скопировать полный custom PostgreSQL dump (все таблицы,
   включая учётные записи, журнал, архив продаж и прогнозов) и manifest.
   Восстановить в новую БД на изолированном экземпляре, проверить количества,
   крайние даты истории и возможность расшифровать собственные интеграции.
   До переключения не запускать импорт с копией настоящих токенов.
4. **Окно переключения.** Дождаться завершения складских операций/переноса грузов.
   Остановить локальный WMS `scripts/start.mjs` и его планировщики, PG оставить для
   финального dump. Получить финальную согласованную копию и проверить checksum.
   Запуск двух активных WMS с копиями токенов и разными БД создаст расходящийся учёт.
5. **Восстановление и миграции.** Следовать cutover-процедуре
   [RELEASE_OPERATIONS.md](RELEASE_OPERATIONS.md): восстановление только в новое
   имя БД, затем выбор этого имени в том же защищённом env. Сохранить старую БД,
   том, пароль и master-key. Запустить `deploy.mjs --ingress none` сначала без
   публичного доступа, проверить миграции/health и существующие учётные записи.
6. **Публичный HTTPS.** Только после проверки данных подключить выбранный ingress,
   домен и сертификат. Для новой пустой установки создать первого руководителя
   через защищённый административный доступ до открытия публичного домена.
   Общего начального пароля или публичной автоматической регистрации нет.
7. **Складской smoke.** Руководитель входит со своего телефона и ПК; сотрудник
   видит только свою/свободную работу. Проверить реальный QR зоны, паллеты/короба,
   маршрут, один управляемый рабочий сценарий без фиктивного списания, печать
   75×120, камеру и HID. Создать backup после проверки, получить rollback point.
8. **Наблюдение.** Убедиться, что проходят получасовой импорт, расчёт ML и
   автоматическая очередь; проверить возраст последнего успешного обновления,
   ошибки/429, свободное место и логи. Настроить уведомления после выбора хоста;
   текущие healthchecks ещё не заменяют внешнее наблюдение.

## Backup и восстановление

Перед каждым обновлением deploy останавливает writers и сохраняет полный dump.
Для ежедневных копий подготовлены `scripts/backup-daily.mjs` и примеры unit/timer
в `infra/systemd/`. После выбора Linux-хоста указать правильные пользователя,
пути Node/репозитория/env/каталога, установить units без `.example`, включить timer
и вручную проверить service. Docker group даёт привилегированный доступ к хосту;
скрипты не создают пользователя и не выдают эти права автоматически.

Пример расписания —02:15 по времени сервера; `Persistent=true` догоняет пропуск.
Копии не удаляются автоматически. Отдельно выбрать retention, зашифрованное
offsite-хранилище, контроль свободного места и уведомления при сбое. Master-key
и env хранить отдельно от dump. Регулярно выполнять restore drill на отдельной БД.

Не выполнять `down -v`, `prune`, удаление/переименование рабочей БД ради отката.
Смена образа назад не возвращает схему и данные назад. При ошибке миграции
сервисы остаются остановленными; исправляется совместимая версия либо
восстанавливается проверенный backup в новую БД по отдельному решению.
