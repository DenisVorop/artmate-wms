# Журнал заданий

## Запрос

Хранить время каждого скана и действия по заданию. Руководитель должен видеть, на каком шаге остановился сотрудник. Нельзя делать вывод об уходе со склада по отсутствию последующих сканов.

## Реализация

- Отдельная таблица `task_history`, индекс по виду/ID задания и времени. Одна отметка `task_history_since`, без восстановления выдуманных старых сканов. Существующие миграции и schema19 не переписываются. Общая резервная копия PostgreSQL включает журнал.
- Принятые складские действия записываются той же транзакцией, что состояние и ответ команды. Бизнес-ошибка откатывает изменения до savepoint, но сохраняет отклонённую попытку. Сбой SQL откатывает всё.
- Повтор команды с прежним requestId не дублирует результат. Разные сканы одинакового товарного штрихкода сохраняются отдельно.
- В рабочем интерфейсе также сохраняются входящие коды, включая промежуточные локальные шаги приёмки, перемещения и инвентаризации. Сначала сервер подтверждает запись кода, затем запускается обработка шага. Если запись не удалась, скан остаётся непринятым для повторения.
- «Получен» означает только получение кода с телефона. «Принято» относится к серверной складской команде, «Ошибка» — к отклонённой команде. Входящий скан не меняет остатки и выработку.
- Время HTTP-запроса берётся на сервере до ожидания очереди, хранится UTC, отображается с секундами в Europe/Moscow. Это время получения сервером, а не доказательство физического сканирования в конкретную секунду.
- Автор HTTP-события определяется сессией. Запись входящего скана разрешена только исполнителю соответствующего задания. Чтение журнала — только руководителю. CSRF, Origin, строгие DTO и проверки владельца сохраняются. В журнал не передаются пароли, cookies, интеграционные ключи или полный body команды.
- `GET /api/task-history?kind=...&id=...&page=1`: страницы по 50 строк. `POST /api/task-scans`: регистрация кода без складской мутации. Записанные события не редактируются и не удаляются через приложение, TTL отсутствует.
- «Журнал» доступен в общей таблице заданий и в карточках сборки, приёмки, размещения, перемещения, отгрузки и инвентаризации. Обновление раз в 5 секунд только при открытом журнале. Модальное окно вынесено в portal, чтобы таблица страницы не меняла его колонки.

## Проверки

Адресные тесты: повтор скана/команды, одинаковые товарные штрихкоды, ошибки без изменения остатков, откат частичной SQL-записи, автор из сессии, CSRF, запрет чужого задания и чтения сотрудником, строгий DTO, отсутствие изменения revision при записи входящего кода. Полные результаты и браузерная проверка дополняются после выполнения.

## Ограничения

Новые события сохраняются после включения версии с журналом. Старый commands хранит отдельные снимки состояния, но не полный текст всех сканов; не импортируем их как якобы точную историю. Непришедший на сервер код (нет связи/закрыт браузер) журнал не подтверждает. Показать прошлое время физического ухода или автоматически обвинить сотрудника журнал не может.

Production не менялась в рамках этой задачи; выкладка требует отдельного запроса пользователя.

## Результат проверки

- Полный прогон: API 609 pass / 2 optional PostgreSQL skip, Web 473 pass; ошибок нет.
- Swagger → Orval, TypeScript обоих приложений, FSD lint, сборка API и штатный Next/Turbopack build успешны. Webpack не применялся: его CSS-проверки отличаются от штатного сборщика; зависимости скопированы в изолированную копию для штатного Turbopack.
- Production-сборка на отдельной базе в памяти: `/tasks` → «Журнал» показывает создание, взятие, сканы паллеты/короба/товара, принятый товар и ошибочный код. На узком экране таблица прокручивается внутри модального окна, страница не переполняется. Escape закрывает окно и возвращает фокус на кнопку задания; ошибок консоли при проверке нет.
- Во время проверки найдено влияние CSS внешней таблицы на таблицу журнала; исправлено portal в body и явными ширинами колонок. Повторная проверка подтвердила исправление.
- Скриншот примера: `output/task-history-preview.jpg` в пользовательской рабочей папке, тестовые данные. Результаты фонового сбоя, нагрузка и физический iPhone отдельно не измерялись; это не считается пройденной проверкой.
- После последних изменений дополнительно прошли 14 адресных тестов журнала и инвентаризации. Отдельно проверено сохранение всех событий и даты начала истории после закрытия/повторного открытия файловой базы, затем replay прежнего скана без дубля.
