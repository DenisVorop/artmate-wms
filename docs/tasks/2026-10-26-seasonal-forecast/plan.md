# План реализации

Исходная WMS сохранена до начала: HEAD `1e8c9cc`, рабочее дерево чистое. Не создавать пустой коммит ради повторного сохранения. Каждый завершённый этап проходит проверки и получает отдельный локальный Conventional Commit.

## 1. Контракты и постоянный архив
- Отдельный серверный модуль `forecasting/`, отдельные SQL-таблицы; не расширять складской WorkspaceDto историей продаж.
- Хранить provider/store/externalId/date/metric/source, только количества, даты и идентификаторы товара; покупателей/адреса/суммы оплат не сохранять.
- Метрики operational ordered/cancelled и financial sold/returned не смешивать. Не переписывать историю за пределами полученного диапазона.
- Дедупликация по стабильному исходному идентификатору, атомарная запись страницы с курсором. Покрытие периодов отдельно от фактов: unknown не равно 0.
- Архивировать каждую полную обычную загрузку; исторические количества не начисляют складской остаток. Сохранять наблюдения наличия с момента включения, прежние stockouts не выдумывать.
- Отдельный идентификатор магазина/источника; замена аккаунта и смена версии ключа не могут смешать историю разных источников.
- Проверки: повтор диапазона, исправленная отмена, частичная ошибка, откат, изоляция магазинов/метрик, сохранность склада/ключей/replay, миграция пустой и существующей базы.

## 2. Возобновляемая историческая загрузка
- Долговечные задания и месячные части с page cursor, lease, состоянием доступа и полнотой. Один сетевой шаг/страница вне SQL lock, атомарное сохранение результата и продолжения внутри.
- Ozon: отдельный read-only адаптер истории FBO v3, без повторной загрузки каталогов/остатков/поставок на каждую страницу. Месячные интервалы с преобразованием MSK↔UTC, лимит страницы 100, has_next/cursor и защита циклов.
- WB: накопление последних доступных оперативных заказов плюс финансовые продажи/возвраты с 29.01.2024. Finance-история требует отдельного подтверждения чтения «Финансы»; не расширять доступ без пользователя.
- До разрешения Finance сохранять явный статус «Нужен доступ к истории WB», продолжать Ozon и разработку остальных этапов.
- Использовать общую paced-очередь; актуальное обновление имеет приоритет, историческая загрузка не запускает пересекающийся импорт одного подключения. Отключение/замена ключа отбрасывает старые результаты.
- Исторические пустые страницы не доказывают, что магазин существовал и товар был доступен: учитывать покрытие/первое наблюдение и качество.
- Проверки: перезапуск на границе страницы, истёкший lease, отказ доступа, 429, поздний ответ после смены подключения, полнота месяцев, отсутствие дублей/секретов.

## 3. Витрина качества и сопоставление
- Собрать дневные ряды с полными московскими днями и происхождением показателя; по каждому магазину отдельно.
- Пропуски загрузки, отсутствие продаж и отсутствие товара различаются. Старые карточки требуют mapping к действующим тематикам, название только предлагает связь.
- Совместимые ряды суммируются по тематике после unitsPerItem; цена/акции/реклама используются только при реально загруженных данных.
- Отобразить начало/конец/число дней истории, незавершённые части, понятную причину недостатка данных. Для новых товаров — объяснимый fallback; чужую тематику не подставлять молча.

## 4. Детерминированный движок моделей
- Чистый TypeScript-модуль, без доступа к SQL/секретам/UI; вход — известный дневной ряд и параметры, выход — дневной прогноз, суммарная потребность и качество.
- Кандидаты: текущее среднее; прошлогодний сезон; сезон с ограниченной поправкой на текущий рост; небольшая обучаемая ridge-модель с календарными/сезонными признаками и трендом.
- Минимальный объём и покрытие истории у каждого кандидата; годовую сезонность нельзя объявлять выученной по 56 дням. Два неполных года означают ограниченную уверенность.
- Прогноз неотрицательный, рост ограничен и затухает; нет повторного умножения уже учтённой сезонности. Дневной прогноз учитывает переходы календаря/високосные даты.
- Профиль «Новый год» имеет настраиваемый круглогодичный минимум, как нижнюю границу цели, а не второе слагаемое.
- Проверки: постоянный ряд, рост/спад, календарный пик, нули, редкий спрос, пропуски, stockouts, новый SKU, выбросы, високосный год, одинаковый результат одного входа.

## 5. Честная оценка и выбор
- Rolling-origin: прогнозировать будущее только по префиксу истории, сравнивать горизонты 7/28 дней и рабочий горизонт, когда данных достаточно.
- Сравнивать с фактом, а не только согласие моделей между собой. MAE в штуках, WAPE при ненулевом спросе, bias и число проверенных окон.
- Не перемешивать даты случайно и не давать будущие признаки обучению. Сохранить параметры, версию алгоритма, fingerprint набора и дату расчёта; поздние исправления источников явно ограничивают точность имитации прошлого.
- Сезонный/ML кандидат допускается к активному плану только при достаточном числе окон, покрытии и устойчивом улучшении базового метода. Иначе fallback с понятной причиной.
- Слабые/несопоставимые financial/operational ряды не делают seasonal-доступ достоверным. Обучение новой версии не портит ранее сохранённую проверенную.

## 6. Интеграция с планом сборки
- Отдельный чистый forecast context передаётся серверному планировщику. Складские вычеты (остатки площадок, в пути, готовое, draft-резервы, НЗП) сохраняются ровно один раз.
- Минимальный запас применяется к цели; затем обычные вычеты и округление до целых коробов.
- Исходные dataComplete/canCreate, свежесть, неизвестные поставки, FIFO и proposalHash сохраняются; новая модель не даёт обхода авторизации и не создаёт заданий автоматически.
- Forecast/model/config/history revision входят в идентичность предложения. Изменение модели между показом и созданием требует нового подтверждения предложения, как и новый складской revision.
- При недостатке годовой истории простая модель остаётся рабочей; пользователь видит, что сезонность для строки ещё не подтверждена.

## 7. Простой интерфейс FSD
- Nest DTO/Swagger — единственный источник; web только через Orval и runtime guards. entities/forecast для чтения, features/forecasting для настроек/загрузки/сравнения, _pages только композиция.
- Основной план: число коробов, покрытие/понятная причина и доступное действие. Служебные cursors, enums, ошибки API и коэффициенты скрыты.
- Детали: история и загрузка, график факт/прогноз, сравнение ошибок моделей, настройка минимального запаса по SKU. Сохранять существующий тёмный стеклянный интерфейс.
- Телефон сотрудников не получает финансовую историю или управленческие настройки. Все endpoints manager-only, POST с CSRF и серверной перепроверкой роли после ожидания.
- Ошибки показываются явно, потеря сессии очищает кэш/поздние ответы. Запросы UI не начинают историю из effect.

## 8. Проверка, реальная история и выпуск
- Поэтапно запускать целевые тесты, api:generate, check-types, lint, test, build; генерацию Swagger/Orval выполнять последовательно.
- Независимое ревью статистики, авторизации и миграций. До изменения рабочей базы — read-only контрольные суммы старых таблиц; новые archive/config таблицы исключаются из сравнения.
- Установить проверенную версию, проверить UI руководителя и неизменность employee flow, сохранить screenshots. Не менять соседний artmate-monorepo/секреты.
- Запустить реальную постепенную историю, проверить несколько месяцев с кабинетами; отсутствие Finance-разрешения не объявлять загруженным WB-архивом.
- Показывать модели и прогноз как проверенные только после фактической догрузки/оценки; оставшуюся фоновую работу и ограничения сообщить честно. Каждый готовый этап — отдельный коммит, без push.
