# WB / Ozon: подтверждение адаптеров, 25.10.2026

## Каталог и идентичность

WB externalId = nmID/nmId. Каталог `POST content-api.wildberries.ru/content/v2/get/cards/list`: cursor.limit100, сортировка ascending, filter.withPhoto=-1. Следующая страница получает updatedAt/nmID предыдущего cursor. Завершение — cursor.total меньше100. Архивные/Ozon discontinued карточки тоже могут отсутствовать в актуальных остатках, поэтому без явного подтверждения остатка они блокируют расчёт соответствующей тематики. Корзина WB в этом методе отсутствует; исторические артикулы из заказов сохраняются с ограниченными описательными данными.

Ozon externalId = SKU, не product_id. `POST /v3/product/list` (visibility ALL) получает product_id; курсор last_id до пустой страницы. Не зависит от deprecated result.total (его отключение запланировано на23.11.2026). `POST /v3/product/info/list` получает до1000 product_id, items содержит sku,name,offer_id,barcodes. Подробности запрошенных товаров должны присутствовать полностью, иначе snapshot отклоняется.

Каталог сам по себе не привязан к FBO/FBW, поскольку карточка может продаваться по нескольким схемам. Фильтрация схемы выполняется именно на фактах спроса и остатках. Связи SKU с WMS задаёт руководитель.

## Остатки

WB `POST seller-analytics-api.wildberries.ru/api/analytics/v1/stocks-report/wb-warehouses`, nmIds=[], limit10000, offset до неполной страницы. Официальный максимум250000строк; меньшая страница ограничивает память. Данные обновляются примерно раз в30минут. Строка — размер/склад, агрегируем по nmId/warehouseId. quantity — доступные покупателю единицы; inWayToClient — доставка покупателю; inWayFromClient — обратная доставка. Оба НЕ входящие поставки продавца. inboundUnits/reservedUnits=null, coverage.inbound=false. На момент проверки документация допускает агрегированный warehouseId=-999999 и имя«Склад WB»; нельзя обещать физическую разбивку, которой источник пока не предоставляет. Повтор одной пары товар/размер/склад отклоняется, чтобы не удвоить остаток.

Ozon `POST /v1/analytics/stocks` получает пакет до100 SKU, без дополнительных фильтров. Метод FBO, данные в реальном времени согласно актуальной документации. available_stock_count — доступно к продаже, transit_stock_count — поставки в пути. Только второй попадает в inboundUnits; requested_stock_count (заявки), inbound_replenishment (перемещения), outbound_pending_delivery (клиентская доставка) туда не входят. Резервы неизвестны/null. Повтор SKU/warehouse отклоняется: нет подтверждённой аддитивной семантики таких дублей. Нет строки для SKU — явная строка с null количествами, а не выдуманный ноль. coverage.inbound=true только при подтверждении transit для каждой строки.

Отсутствие строки остатка не подтверждает0. Аналогичное правило применяется к WB. coverage.stocks означает, что компонент запроса дочитан, а не что для любого каталожного SKU известен остаток; планировщик обязан проверять null отдельно.

## Спрос, даты, отмены и возвраты

Период адаптера:1..89 полных календарных дней Europe/Moscow, to раньше текущего дня. Для WB from также ограничен последними89полными днями, поскольку доступная оперативная история хранится90дней с оформления, а пограничный90-й день может уже быть неполным.

WB `GET statistics-api.wildberries.ru/api/v1/supplier/orders` и `/sales`, flag0, начальный dateFrom = fromT00:00:00 (Москва). Продолжение — полная lastChangeDate последней строки, до пустого массива; не останавливаемся на«меньше80000», поскольку лимит в документации условный. Циклический/непродвигающийся курсор — ошибка, частичный snapshot не сохраняется. Пограничные повторы дедуплицируются по srid (orders) или saleID(sales). После выгрузки фильтруем фактическое поле date по запрошенным календарным дням. Только warehouseType«Склад WB»;«Склад продавца» исключён; неизвестная схема исключается с coverage.demand=false. Одна строка — одна единица. orderedUnits включает все заказы, cancelledUnits — отменённую часть этой когорты. S/R в saleID разделяет продажу и возврат, эти события относятся к собственной date. Оперативная статистика предварительная и может не содержать неподтверждённую оплату, это явно предупреждается. Факты продаж не выдаются за точный финансовый отчёт.

Ozon `POST /v3/posting/fbo/list`: cursor+has_next, limit100. Именно v3: официальная страница legacy v2 объявляет отключение31.08.2026. Диапазон fromT00:00:00+03:00 .. toT23:59:59.999+03:00 преобразуется в UTC RFC3339, дата нормализации обратно Москва. Никакие FBS endpoints не вызываются. Заказы сторонних платформ с external_order.is_external=true исключаются. Количество — products.quantity; cancelledUnits — часть заказанных единиц, у которых текущий status=cancelled; данные группируются по created_at, не дате изменения статуса. Из этих postings нельзя достоверно получить финансовые выкупы и все возвраты: soldUnits=null, returnedUnits0 — только техническое значение ограниченного контракта и сопровождается явным предупреждением. Планировщик использует orderedUnits−cancelledUnits, не трактует returnedUnits0 как подтверждение отсутствия возвратов.

В следующих загрузках исторические отмены могут измениться; период должен заменяться как snapshot, а не складываться с предыдущей загрузкой. Полные исторические продажи без влияния отсутствия товара, акции/сезонность и финансовая сверка в эту первую версию не входят.

## Транспорт и проверка

Только жёсткий allowlist HTTPS origins+paths, GET либо read-only POST. redirect=error. Не принимать пользовательский baseURL. ТаймаутHTTP30сек, всего240сек, до180запросов, ответ до20МБ и суммарно до80МБ за загрузку. Ограниченные страницы/cursorprogress, отказ при неожиданной схеме, статусах401/403/429/5xx. Ошибки только собственные фиксированные фразы: upstreambody,headers,URLs и исходные исключения не возвращаются. Сигнал отмены передаётся в fetch. WB реальные запросы ограничиваются паузами60.1сек для статистики,20.1сек аналитики,650мс контента. Базовый токен может иметь более жёсткие ограничения:429 приводит к безопасному отказу, без циклических retry. Для работы рекомендуется персональный read-only токен с Контент/Статистика/Аналитика и соответствующий read-only ключ Ozon с FBO/catalog/analytics.

Unit tests только mock fetch и фикстуры; в них нет реальных ключей и внешней сети. Они подтверждают нормализацию, FBS-фильтр, курсоры/дедуп, unknown/null, безопасность ошибок, дату, abort. Это не подтверждение успешного реального подключения магазина.
