# Release operations

Все команды запускаются из корня WMS. Это локальные команды Docker на выбранном
хосте, не SSH-клиент и не автоматическое разрешение на публикацию.
Отдельный ручной SSH workflow и GitHub secrets описаны в
[GITHUB_DEPLOYMENT.md](GITHUB_DEPLOYMENT.md). До выбора
площадки можно проверять файлы и собирать образы. Не запускать production-команды
против существующей рабочей БД ради проверки.

## Подготовка конфигурации

Нужны Node.js, Docker Engine с Compose v2, опубликованные образы API/web,
отдельный каталог WMS и достаточно места для БД и резервных копий.

```bash
node scripts/release/init.mjs --domain wms.example.com --env-file .env.production --new-install
```

`--new-install` означает действительно пустую новую установку. Для переноса
существующей БД **вместо него** импортировать исходный raw-файл ключа шифрования:

```bash
node scripts/release/init.mjs --domain wms.example.com --env-file .env.production --existing-key-file /secure/original-marketplace.key
```

Файл ключа должен содержать ровно 32 исходных байта и иметь права `600`. Команда
сохраняет этот же ключ в base64 в `WMS_MARKETPLACE_KEY`, создаёт новый пароль БД,
не выводит секреты и не перезаписывает существующий env-файл. Отсутствие исходного
ключа нельзя исправлять генерацией нового: сохранённые токены маркетплейсов
перестанут расшифровываться. Перед переносом уточнить путь исходного файла в
действующем приложении; не брать ключи Artmate-monorepo.

В защищённом `.env.production` заменить placeholders двух image-переменных на
опубликованные `:sha-<commit>` или `@sha256:<digest>`. `latest`, незакреплённые
образы и примеры не пройдут preflight. Digest даёт наиболее строгую фиксацию;
SHA-теги также не должны перезаписываться в registry.

```bash
node scripts/release/preflight.mjs --env-file .env.production
```

Проверяются обязательные значения, форматы ключа и пароля, права env-файла,
Compose config и наличие Compose. Контейнеры не меняются. Env нельзя делать
общедоступным, коммитить, присылать в чат или выводить через `compose config`
без `--quiet`. Для production всегда передавать файл явно.

## Запуск версии

```bash
mkdir -m 700 /secure/wms-backups
node scripts/release/deploy.mjs --env-file .env.production --backup-dir /secure/wms-backups
```

По умолчанию `--ingress none`: базовый Compose не публикует порты. Для отдельного
сервера выбрать `--ingress edge`; он добавляет `infra/compose.edge.yml` и запускает
Caddy после внутренних smoke-проверок. Для соседства с Artmate выбрать
`--ingress artmate`; он добавляет `infra/compose.artmate.yml`, подключая web к
существующей external-сети. Внешний Caddy и DNS Artmate настраиваются отдельно
по основному deployment guide. Не запускать второй Caddy на уже занятых 80/443.
Для каждого обновления сохранять выбранный ingress-режим.

Все операционные CLI принимают `--project-name` (по умолчанию `artmate-wms`).
Уникальное имя использовать для изолированного smoke/restore drill, передавая
его каждой команде. Допускаются только строчные буквы, цифры, `_` и `-`.
Подмена имени не изолирует вручную настроенные external-сети: smoke запускать
с `--ingress none`, без подключения к сети действующего Artmate.

Порядок обновления:

1. Проверка конфигурации и загрузка образов.
2. Запуск и readiness PostgreSQL.
3. Остановка `api` и `web` с таймаутом 120 секунд.
4. Согласованная custom/compressed-копия существующей непустой БД.
5. Одноразовые миграции `migrate` с profile `tools`.
6. Запуск `api`/`web`, ожидание healthcheck, внутренние запросы API readiness,
   web healthz и маршрута сессии через web proxy.
7. Запуск standalone Caddy, если выбран `edge`.

Это короткое окно недоступности. Встроенные фоновые задачи останавливаются вместе
с API; не запускать параллельно другой API/worker или внешние writers к той же БД.
Не выполнять два release/restore одновременно. На свежей БД backup не создаётся,
поскольку ещё нет прикладных таблиц. При ошибке любого шага следующие не
выполняются. После ошибки миграции нет автоматического запуска старого образа или
отката схемы: выяснить состояние, исправить причину и повторить совместимую
версию. При сбое внутреннего smoke ingress не запускается впервые, но уже
работающий внешний прокси не останавливается автоматически.

Скрипты не делают `down -v`, prune, автоматический drop, rollback или SSH.
Публичный HTTPS, camera permissions, вход сотрудника, печать и первый реальный
складской сценарий проверяются после публикации отдельно. Нельзя считать
внутренний healthcheck полной проверкой пользовательской операции.

## Резервное копирование

```bash
node scripts/release/backup.mjs --env-file .env.production --output /secure/wms-backups/manual.dump
```

Выполняется `pg_dump --format=custom --compress=6`. Готовый dump появляется
атомарно, без перезаписи, вместе с `.manifest.json`: время, имя БД, размер и SHA256.
Оба файла с правами `600`; при ошибке временные файлы удаляются. Custom dump уже
сжат: дополнительный gzip не нужен. Ручная копия может выполняться во время
работы приложения; PostgreSQL делает согласованный снимок. Перед релизом writers
остановлены, чтобы копия соответствовала точке переключения.

Dump содержит всю БД, включая чувствительные данные и зашифрованные credentials.
Права `600` не заменяют шифрование диска/backup-хранилища. Сохранять копию вне
основного VPS и проверять восстановление. Ключ `WMS_MARKETPLACE_KEY` и остальные
нужные production-секреты **не включены** в dump или manifest: сохранить их
отдельным защищённым каналом вместе с планом восстановления.

## Безопасная проверка восстановления

Остановить `api` и `web` выбранного проекта, убедиться, что миграции не запущены.
Скрипт повторно проверит состояние Compose. Он принимает только **новое,
несуществующее имя БД**; существующая БД не перезаписывается даже если пустая.

```bash
node scripts/release/restore.mjs --env-file .env.production --input /secure/wms-backups/manual.dump --target-database wms_restore_check --confirm RESTORE:wms_restore_check
```

Сначала проверяются права и SHA256, явное подтверждение, остановка writers и
отсутствие целевой БД. Затем создаётся новая БД и выполняется transactional
`pg_restore --exit-on-error --single-transaction --no-owner --no-privileges`.
Сервисы остаются остановленными. Если импорт не удался, скрипт не удаляет БД и не
запускает приложение. Для повторения выбрать новое имя после выяснения причины.

### Первичный перенос и переключение на восстановленную БД

При переносе локальной WMS сначала подготовить согласованный custom dump всех
данных и сохранить исходный ключ. Создать production env через
`init --existing-key-file`, затем указать опубликованные образы. Запустить только
PostgreSQL базового Compose, без API, web и внешнего доступа:

```bash
docker compose --project-name artmate-wms --env-file .env.production -f infra/compose.yml up -d --wait postgres
node scripts/release/restore.mjs --env-file .env.production --input /secure/import.dump --target-database artmate_wms_import --confirm RESTORE:artmate_wms_import
```

Для импорта требуется парный checksum manifest от `backup.mjs`. Перенос с другой
машины выполняется защищённым каналом; файлы снова проверить перед импортом.
Не переключать рабочие операции одновременно на локальном и серверном экземпляре:
выбрать точку остановки локальных writers и сделать окончательный снимок.

После успешного восстановления оператор проверяет содержимое и принимает решение
о переключении. В том же защищённом `.env.production` изменить **только**
`POSTGRES_DB=artmate_wms_import`; пароль production PostgreSQL, исходный
`WMS_MARKETPLACE_KEY` и остальные секреты сохранить. Не запускать повторно
`init --new-install` и не создавать новый volume.

```bash
node scripts/release/preflight.mjs --env-file .env.production
node scripts/release/deploy.mjs --env-file .env.production --backup-dir /secure/wms-backups
```

`POSTGRES_DB` допускает произвольное несистемное имя: строчная буква, затем
строчные буквы, цифры и `_`, максимум 63 символа. `postgres`, `template0` и
`template1` запрещены. Compose передаёт выбранное имя в API, команды и healthcheck.
На уже созданном volume изменение `POSTGRES_DB` не инициализирует PostgreSQL
заново: новая целевая БД должна быть заранее восстановлена, что выше и сделано.
При deploy снимок восстановленной БД сохраняется перед применением миграций.

Внутренние smoke должны пройти до настройки внешнего доступа. Затем проверить
пользователей, количество товарных/складских записей, историю продаж, даты,
расшифровку интеграций с исходным ключом и критичный складской сценарий. Для
публикации повторить deploy с выбранным `--ingress edge` или `--ingress artmate`
согласно основному deployment guide.

Прежние БД и volume сохраняются: команды не переименовывают и не удаляют их.
Переключение не выполняется самим `restore`, а требует явного изменения env и
запуска deploy оператором. Возврат env на старую БД — отдельное решение после
проверки совместимости схемы/образов и новых складских операций: это не безопасный
автоматический rollback. При обычном restore drill не менять production env и
не запускать приложение на проверочном снимке.

## Проверки tooling без Docker и реальных данных

```bash
node --test scripts/release/release.test.mjs
```

Тесты запускают настоящие CLI с Docker-stub в отдельном временном каталоге:
порядок деплоя, остановка при ошибке, неизменность ключа при импорте, запрет
перезаписи, очистка неудачного dump, checksum, защита восстановления и отсутствие
секретов в выводе. Они не заменяют Docker build и restore drill на отдельной БД.
