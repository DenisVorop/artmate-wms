# 060. Подбор хранения по проходам и ярусу

Физическая совместимость из physical.ts остаётся обязательным первым фильтром: размеры, высота, масса, тематика, профиль коробов, фактическая занятость и входящие резервы. Для новых назначений сервер применяет placement-ranking.ts; размещение подтверждается прежними командами. Паллета своей тематики сохраняет первый приоритет среди адресов, не исключённых подтверждённым разрывом пути.

Внутри тематической группы известный маршрут предшествует неизвестному. Оценка выбора = длина пути + 12 условных метров за каждый ярус выше первого. Напольное место и первый ярус не получают штрафа. Это мягкая стоимость дополнительной работы, не реальная длина пути и не норматив времени. Затем предпочтение отдаётся минимальной подходящей высоте и стабильному коду адреса.

placement-routing.ts строит ограниченный ортогональный граф свободных ячеек по общей схеме. Один Dijkstra обслуживает все цели. В помещении с нанесёнными проходами основная сеть состоит из проходов; в коридоре доступен свободный пол. В помещении без проходов путь оценивается по свободному полу с пометкой floor. Стеллаж — одно препятствие для всех ярусов; отдельные активные места тоже препятствия, включая заблокированные. Архивные объекты исключены, повороты используют общий footprint.

Между помещениями путь существует только через положительный участок реального проёма общей стены. Один Entrance открывает обе смежные стороны; углы и зазоры не соединяются. Проём разбивается по границам оборудования и проходов: частично перекрытая середина не закрывает весь широкий проём. Короткий подход от места/двери к нанесённому проходу ограничен 2 м. Концы маршрута не становятся мостом между разорванными проходами. Модель хранит число сторон доступа без конкретного фронта, поэтому расстояние до края места остаётся оценкой; габарит транспорта и радиус поворота не моделируются.

aisles/floor означают найденный путь, unknown — неизвестный источник, неполную геометрию/подход или исчерпание лимита; unreachable — разрыв нанесённой сети при доступных концах. Защита ограничивает весь запрос: 1000 целей, 10000 объектов, 12000 ячеек, 60000 узлов и 2 миллиона проверок. Лимит даёт unknown, а не фиктивную недостижимость. Для unknown сохраняется выбор по теме, ярусу и полезной высоте; distanceMeters=null. Прямая через стену не подставляется.

Начало размещения коробов — fromLocationId. Начало приёмки — единственный активный адрес точной привязанной зоны receipt+pallet; при отсутствии привязки допустим единственный активный receiving-адрес. Неоднозначную зону нельзя подменить адресом из другой зоны. Источник не является позицией сотрудника.

Подбор выполняется по полному серверному state, включая скрытые от сотрудника резервы; claim повторяет его внутри общей SQL-транзакции. Claimed/in_transit сохраняют toLocationId даже после изменения карты: GET не переназначает переносимый груз. Подтверждённо недостижимые адреса остаются в физически подходящем списке для ручной приёмки, но не предлагаются автоматически. При размещении коробов без маршрута claim сообщает о проходах/проёмах без побочных изменений; existing carry подтверждается по прежним физическим правилам.

GET placement-options содержит nullable recommendation с исходным/целевым ID, routeStatus, distanceMeters, ярусом, отдельным условным весом и объяснением. Swagger → Orval, без ручных общих контрактов. Руководитель видит объяснение в существующей рекомендации. Схема БД, FIFO, история, cached responses и баланс не мигрируют.
