# ADR068 — архив спроса и проверяемый сезонный прогноз

Дата: 2026-10-26. Статус: принято.

## Решение

История маркетплейсов хранится отдельно от Workspace в SQL-таблицах forecast_history_facts, forecast_history_coverage, forecast_history_jobs, forecast_history_pages и forecast_stock_observations. Полный текущий snapshot архивируется в его транзакции публикации. Повторные страницы не удваивают факты. Исторический месяц публикуется атомарно после завершения всех страниц; промежуточные страницы не участвуют в обучении. Исправления завершённого месяца заменяют прежние факты того же источника и магазина.

Наблюдение хранит магазин, площадку, внешний товар, календарный день Москвы, метрику и источник. Заказы, отмены, выкупы и возвраты различаются. Report date WB не доказывает покрытие sale date; финансовые строки не превращают отсутствие события в нулевые продажи. Неизвестная доступность не объявляется наличием, а известный stockout не становится низким спросом.

История загружается возобновляемыми заданиями небольшими страницами. Текущий получасовой импорт имеет приоритет. Между архивными заданиями выбирается самое давно ожидающее, чтобы большая история одного магазина не задерживала другой; первоначальный архив остаётся приоритетнее ежедневного сопровождения. Сеть работает вне общей SQL-транзакции с существующей последовательной очередью, таймаутами и cooldown. Данные другого магазина исключаются из активного расчёта. Финансовый WB ключ отдельный, readonly, AES-GCM с привязкой к history store. Перед сохранением SID действующего и нового ключа сверяются через официальный seller-info; после сети повторно проверяются полномочия и версии подключения. Ключ не входит в Workspace, DTO, worker payload, replay registry браузера или логи.

Чистый TypeScript движок сравнивает средний спрос, прошлогоднюю сезонность, сезонность с текущим ростом и небольшую регуляризованную регрессию. Выбор основан на rolling-origin проверке без будущих данных; ошибка измеряется на 7, 28 и рабочем горизонте. Недостаточная история, пропуски и отсутствие надёжного преимущества оставляют средний спрос. Финансовый прогноз не подменяет оперативные заказы; преобразование между метриками допустимо только отдельной калибровкой с проверкой на оперативном факте.

Тяжёлый расчёт выполняется в worker вне SQL и основного event loop. ForecastScheduler создаётся без побочных эффектов; только main запускает его и завершает до закрытия БД. Input key включает завершённую историю, активные магазины/версии, mappings, настройки, упаковку, политики и полный день Москвы. Публикация повторно сверяет key и lease. Устаревший кэш не используется; план временно применяет прежнее среднее и минимальный запас.

forecast_policies хранят минимальное число коробов и разрешение сезонности. Для «Новый год» начальный минимум — один короб, остальные — ноль; руководитель может изменить. Минимум — нижняя граница общего целевого запаса, не дополнительный расход поверх спроса.

План сборки вычитает остатки площадок, поставки в пути, готовые короба, черновые отгрузочные резервы и незавершённые задания ровно один раз. Проверки неизвестных данных, свежести, размещённого сырья и FIFO сохраняются. proposalHash включает forecast key и применённую цель: изменение политики, истории или публикация модели делает старое предложение недействительным. Прогноз не создаёт заданий автоматически.

Контракт: Nest DTO → Swagger → Orval → runtime guard. Read-only entities/forecast и feature forecasting соблюдают FSD; page объединяет прогноз и сборку. Обычный экран показывает результат, подробности истории и сравнения раскрываются по запросу. Создание архива и изменение политики — явные команды с manager/CSRF/requestId; GET и React effects не запускают загрузку.

## Последствия

Первые месяцы загрузки могут занимать часы из-за ограничений API. Это долговечная фоновая работа, а не обещание мгновенно получить два года. Модель может обоснованно оставить средний спрос даже после полной загрузки. Нельзя обещать точность до проверки на реальных данных; статус и причины отказа видны руководителю.
