# ADR-012 — конструктор и складской учёт

Дата: 23 октября 2026 года.

## Запрос и решение

Владелец запросил изменение размеров склада, входы, коридоры, размещение/поворот стеллажей и удаление мест. В текущем этапе помещение прямоугольное: размеры в метрах задают фиксированные границы плана. Входы привязаны к стенам; проходы рисуются прямоугольниками, которые можно соединять. Стеллажи поворачиваются с шагом 90°. Непрямоугольные наружные стены и расчёт маршрутов техники в этот этап не включены.

Редактирование геометрии изменяет схему, а не адрес паллеты. Идентичность адреса, QR и складская история сохраняются. Остатки и перемещения продолжают изменяться только отдельными складскими командами.

## Удаление

«Удалить с плана» переносит объект в постоянную корзину. Восстановление возвращает прежние ID/коды, если геометрия снова допустима. Занятый адрес, пустой поддон на месте, резерв возврата и незавершённое перемещение запрещают удаление. Завершённая история этому не мешает. Старый код не переназначается другому адресу.

Правила скилла product-design: `rule/destructive-proportional`, `rule/undo-only-when-honest`, `rule/name-object-scope-consequence`. Жесты имеют числовую альтернативу: `rule/gesture-has-control-alternative`. Ошибки сохраняют введённые значения и позволяют исправить причину: `rule/preserve-user-input`, `rule/error-states-recovery`.

## Интеграция с операционными экранами

Workspace содержит активные и архивные объекты для истории и корзины. Отбор адресов для приёмки, перемещений и подготовки отгрузки исключает архив. Загрузка склада и мини-карта обзора считают только активные адреса. Исторические строки продолжают разрешать старые ID в читаемый код. Сервер независимо проверяет архивный статус в складских командах; фильтр web не является защитой учёта.

Название выбранного склада в sidebar и обзоре берётся из warehouse.name. Длинное имя не увеличивает ширину навигации.

## API и совместимость

Источник контракта — NestJS DTO/Swagger, клиент и типы — Orval. Новых совместно используемых контрактов нет. Новые команды используют прежний транспорт с requestId и защитой ручного повтора.

Клиент считает snapshot текущим только при наличии warehouse с допустимыми размерами, aisles и entrances наряду с остальными массивами. Исторические ответы команд v1/v2 по-прежнему распознаются как подтверждение записи, но не заменяют текущую модель конструктора. После успешной команды запрашивается свежий workspace; сбой чтения не превращает сохранённую запись в ошибку сохранения. Добавлена регрессия старого ответа v2.

## Перенос данных

Аддитивная миграция v3 сохраняет все прежние сущности, коды и количества. Первоначальные размеры вычисляются из существующей схемы с запасом и явно остаются редактируемыми демонстрационными значениями. Реальные входы/проходы не выдумываются: при обновлении их списки пустые. Перед основной миграцией — проверка на копии базы и резервная копия. Рабочая БД не используется для очистки тестовых таблиц.

## Версия состояния

Каждая новая успешная команда увеличивает revision в той же SQL-транзакции. Повтор команды возвращает исходную ревизию; ошибки и чтение её не увеличивают. Значение хранится в metadata и не сбрасывается при запуске. Новые поля и типы также приходят через Swagger/Orval.

Одинаковая версия схемы не означает одинаковую свежесть данных. Общий адаптер и polling выбирают snapshot с наибольшей revision: запоздавшее чтение или исторический replay не могут откатить актуальный план, корзину или остатки. При сбое свежего GET подтверждённый более новый ответ команды используется; более старый ответ не перезаписывает кэш. Регрессии проверяют оба пути и конкурентно обновлённый кэш.
