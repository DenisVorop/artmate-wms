# ADR 002: PostgreSQL и атомарные складские операции

Статус: принято для первой интерактивной версии, 23 октября 2026 года.

## Хранение и запуск

NestJS работает с PostgreSQL через `pg`. Для WMS используется отдельная локальная база `postgresql://wms:wms@127.0.0.1:5440/artmate_wms`; адрес переопределяется через `DATABASE_URL`. Скрипты проекта поддерживают отдельный кластер Postgres.app и альтернативный запуск через Docker. API по умолчанию слушает `127.0.0.1:4080`; адрес и порт задаются через `API_HOST` и `API_PORT`.

PGlite нужен только для изолированных тестов и экспорта OpenAPI. Он выбирается явно через `WMS_DATA_DIR=memory://`. Основное приложение использует PostgreSQL. Если передать файловый путь в `WMS_DATA_DIR`, адаптер запишет PGlite в эту директорию; для обычного запуска это значение задавать не следует.

Каждая сущность хранится в своей таблице как ID и документ JSONB: `skus`, `locations`, `lots`, `pallets`, `boxes`, `tasks`, `employees`, `shipments`, `activities`. Такой формат позволяет менять первую версию модели, сохраняя реальную долговечность данных и SQL-транзакции. При инициализации создаётся схема и однократно загружаются демонстрационные данные. До пилота на реальном складе нужны версионированные миграции и ограничения связей на уровне базы. Загруженные примеры не являются остатками физического склада.

## Границы транзакции

Каждая команда читает сущности и сохраняет состояние внутри одной SQL-транзакции. `pg_advisory_xact_lock` последовательно пропускает складские операции из разных экземпляров API. Очередь внутри процесса также предотвращает пересечение транзакций PGlite. Чтение всего snapshot выполняется транзакционно, чтобы ответ не собирался из состояний до и после одной мутации.

Это решение рассчитано на небольшую нагрузку первой версии. Сейчас команда записывает документы всего склада. Следующий этап — блокировки отдельных строк, запись только изменённых сущностей, индексы и неизменяемый журнал количественных движений.

Для каждой мутации обязателен `requestId`. Таблица `commands` хранит отпечаток запроса и ответ после успешной фиксации. Точный повтор получает исходный ответ; повторное использование ключа для другой операции возвращает 409. При ошибке остатки, резервы и события откатываются вместе. Ответ на повтор может описывать более старое состояние склада, поэтому клиенту при необходимости следует повторно запросить snapshot.

## Реализованные правила

- Одна паллета содержит один SKU как до сборки, так и после неё. Смешанный короб содержит несколько партий поступления одной тематики.
- FIFO определяется по `receivedAt`. Резерв задания учитывает другие задания и не позволяет зарезервировать больше свободного товара.
- Перед штрихкодом товара необходимо подтвердить исходную паллету. Когда резерв партии исчерпан, нужно подтвердить следующую паллету: одинаковый штрихкод тематики не должен незаметно менять происхождение товара.
- Сканирование переносит одну раскраску из сырого остатка в открытый короб. Упаковка переносит полный короб в готовую продукцию. Счётчики результата увеличиваются при упаковке.
- При упаковке проверяется уникальный код текущего короба. Переполнение, другая тематика и закрытие неполного короба запрещены.
- Место обозначает конечный адрес одной паллеты. `levels` пока служит характеристикой стеллажа и не умножает вместимость. Полноценная модель отдельных адресов каждого яруса относится к следующему этапу.
- Размещение проверяет занятость, блокировку и доступную высоту. Высота готовой паллеты пока вычисляется по временному профилю: 6 коробов в слое, 300 мм на слой и 150 мм на поддон. Это демонстрационное правило в коде, а не подтверждённая физическая вместимость. Настраиваемые профили упаковки нужно добавить отдельно.
- Создание отгрузки резервирует конкретные короба по FIFO. Подтверждение меняет только запрошенные короба, уменьшает остаток соответствующих паллет и сохраняет остальные короба. Происхождение отгруженного товара остаётся в базе.
- `boxesToday` и `unitsToday` сейчас показывают упакованный результат с момента инициализации демо. Нет смены даты, автоматического обнуления и отдельной сохраняемой сущности смены. Эти поля нельзя считать исторической аналитикой производительности или основанием для оплаты труда.
- Статус сотрудника влияет на возможность выполнения задания и его приостановку. Авторизации, проверки ролей и подтверждённой личности сотрудника пока нет. Эта версия предназначена для локального использования.

## Проверка на PostgreSQL

По умолчанию `yarn test` выполняет тесты в отдельном PGlite в памяти. Для настоящего PostgreSQL адрес задаётся переменной `WMS_TEST_DATABASE_URL`; тесты передают его адаптеру как `DATABASE_URL`.

**Никогда не указывайте в `WMS_TEST_DATABASE_URL` базу `artmate_wms` или любую другую базу с нужными данными.** Тесты выполняют настоящие складские команды: добавляют и изменяют остатки, удаляют документы при сохранении состояния, создают резервы и записи идемпотентности. Автоматического сброса или защиты от ошибочного адреса рабочей базы в тестовом коде нет.

Для воспроизводимого полного прогона нужна пустая отдельная база `artmate_wms_test`. Повторный запуск на уже использованной базе не эквивалентен чистому прогону: первый тест рассчитывает на исходные демонстрационные остатки. Перед каждым полным прогоном пересоздайте **только тестовую базу**. Пример из корня монорепозитория для локального Postgres.app:

```bash
WMS_PG_BIN=/Applications/Postgres.app/Contents/Versions/latest/bin
PGPASSWORD=wms "$WMS_PG_BIN/dropdb" --host=127.0.0.1 --port=5440 --username=wms --if-exists artmate_wms_test
PGPASSWORD=wms "$WMS_PG_BIN/createdb" --host=127.0.0.1 --port=5440 --username=wms artmate_wms_test
WMS_TEST_DATABASE_URL=postgresql://wms:wms@127.0.0.1:5440/artmate_wms_test yarn workspace @artmate-wms/api test
```

Для создания базы пользователь `wms` должен иметь право `CREATEDB`. Путь к утилитам зависит от установки PostgreSQL. Команды `dropdb` и `createdb` выше намеренно содержат буквальное имя тестовой базы, а не переменную рабочего подключения. Не запускайте их одновременно с другим прогоном тестов.

При реализации проверены восемь тестов полным прогоном на отдельном PostgreSQL. Дополнительно пройден тест двух независимых клиентов: конкурентный резерв не превышает остаток, а сохранённое состояние одинаково читается через оба подключения. Этот девятый тест выполняется только при `WMS_TEST_DATABASE_URL`; без переменной он пропускается.

Проверки покрывают FIFO, смешанный короб, сохранение количества при переходах сырьё → незавершённая сборка → короб, запреты неверного источника и переполнения, идемпотентность, конкурирующие резервы, частичную отгрузку, откат неподходящей приёмки, QR, стабильность snapshot и строгую валидацию DTO. Тестовые данные основного демонстрационного приложения для этих прогонов не использовались.

## Ограничения перед работой на складе

Нужно реализовать перемещения паллет, карантин, отмену с освобождением резерва, неизменяемый журнал движений, авторизацию, проверку ролей, промышленные миграции, проверку резервного копирования и восстановления, интеграцию печати и восстановление после ошибок сканера. SVG-метки уже содержат настоящие QR-коды и печатаются через веб-интерфейс.

## Контракт API

Источником описания API служат DTO NestJS и явные аннотации Swagger. Экспорт OpenAPI поднимает контекст приложения без сетевого сервера и использует временный PGlite. Next.js получает клиент и типы через Orval; общего пакета `contracts` нет.

Явно заданные Swagger-типы, типы тела запроса для валидации и токены DI позволяют использовать `tsx`, не полагаясь на автоматическую генерацию метаданных типов декораторов во время выполнения.
