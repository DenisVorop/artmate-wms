# ADR 014 — Нарисованные пространства и стены на рабочем поле

Статус: принято для этапа пространств.

## Пол и рабочее поле

Размеры `WarehousePlanDto.width/depth` задают рабочее поле canvas. В режиме `rectangle` сохраняется прежний прямоугольный пол. В режиме `spaces` пол состоит только из активных `WarehouseSpaceDto`; пустой список допустим и не создаёт помещение автоматически. Нарисованное помещение и коридор имеют собственные имена, площадь и спокойные различающиеся заливки. Архивные участки не рисуются.

Пол и свободный проход `AisleDto` различаются: коридор — участок пола, на котором сервер может разрешить временное хранение; Aisle — свободная зона, запрещающая размещение объектов хранения. Canvas не подменяет серверные проверки размещения.

Подписи участков имеют базовый размер 0,5 м в координатах SVG с уменьшением для узких или коротких участков. Площадь выводится размером 82% от имени. Длина имени ограничивается по доступной ширине и фактическому размеру шрифта; полное имя остаётся в доступном названии и SVG-title. Это сохраняет читаемость портретного плана при вписывании по высоте; увеличение масштаба пропорционально увеличивает подписи без ResizeObserver.

## Интерфейс canvas

`PlanCanvas` сохраняет предыдущие props и получает:

- `drawKind?: 'room' | 'corridor' | null` — текущий инструмент рисования;
- `onDraw?: (draft: SpaceDraft) => void`, где draft содержит kind, x, y, width, depth;
- `selectedSpaceId?: string | null` и `onSelectSpace?: (id: string) => void`.

`SpaceDraft` берёт поля из generated `WarehouseSpaceDto`, не является отдельным общим API-контрактом. Canvas не вызывает create/update и не сохраняет рисунок. Root открывает RHF-форму имени и точных параметров, а запись происходит только после Save.

Участок выбирается через SVG-кнопку с именем, площадью и поддержкой Enter/Space. Во время рисования объекты хранения, свободные проходы и входы не перехватывают указатель; фоном для жеста служат рабочее поле и уже существующие участки. Перекрытие участка можно нарисовать как черновик, но сервер откажет в его сохранении с объяснением.

## Жест рисования

`lib/use-space-drawing.ts` хранит pointer lifecycle и локальный preview. Явный pointermove минимум на 5 экранных пикселей отличает рисование от клика. Начальная и конечная точки переводятся через обратную SVG-матрицу, привязываются к шагу 0,5 м и ограничиваются canvas. Обратный drag нормализуется к верхнему левому углу. Для открытия формы оба размера должны быть не меньше 0,5 м.

Preview показывает размеры и площадь в абсолютном overlay, который не меняет высоту страницы и матрицу SVG. Конечный прямоугольник вычисляется до вызова `onDraw` и открытия формы. Escape и pointercancel освобождают capture и отменяют preview. Простое down/up ничего не создаёт. Кнопка добавления по размерам остаётся альтернативой жесту в root toolbar.

P1-защита обычного клика для перемещения объектов и входов сохранена: без подтверждённого pointermove геометрическая команда не вызывается, а смена выбранной боковой карточки выполняется после расчёта endpoint.

## Стены и проёмы

Для каждого активного участка строятся четыре глобальных отрезка. Коллинеарные пересекающиеся или соприкасающиеся отрезки объединяются с допуском 1e-9. Затем из объединённых физических стен вычитаются глобальные интервалы дверных проёмов. Общая стена двух участков рисуется один раз; вход на любой из её сторон прорезает обе совпадающие границы. Частичные совпадения и соприкасающиеся проёмы обрабатываются тем же алгоритмом.

В `rectangle` алгоритм получает один прямоугольник с началом 0,0. В пустом `spaces` внешние стены canvas не становятся стенами склада: остаётся только приглушённая пунктирная рамка рабочего поля.

## Входы и подсказки размещения

`EntranceDto.spaceId` задаёт участок. В rectangle используется null. Центр входа добавляет глобальные x/y участка к локальным wall/offset. Неверная или архивная привязка не рисует фиктивный вход на границе всего canvas.

При перетаскивании входа сравниваются подходящие стены активных участков в глобальных координатах; результат содержит spaceId, wall и offset. Широкий проём не прикрепляется к короткой стене. При одинаковом расстоянии общей стены сохраняется прежняя привязка, чтобы вход не перескакивал между соседними участками без причины. Сервер проверяет отсутствие дубликата физического проёма и другие ограничения.

Поиск предлагаемого положения объекта хранения сканирует только bounds активных участков, включая коридоры. Объект должен целиком уместиться в одном участке; объединённая площадь соседних помещений не разрешает размещение через стену. Архивные участки и внешняя пустота не учитываются. Поиск ограничен 100 000 кандидатов для защиты интерфейса на полностью занятом большом плане; null означает, что оператору нужно задать параметры вручную или изменить план. Автоматического расширения или заполнения склада нет.

## Проверки и границы

Чистые тесты проверяют глобальные центры входов, перенос между участками, предпочтение прежней привязки на общей стене, объединение полных/частичных стен, вычитание общих дверных проёмов, пустой spaces, поиск внутри коридора и удалённого участка, запрет подсказки через стену, snap/clamp обратного рисунка и минимальный размер. Прежние тесты gesture и rectangle сохранены.

Участки остаются прямоугольниками без поворота. Произвольные многоугольники, маршрутизация техники и физические проверки нормативной ширины проходов не входят в этот этап. Сохранение и целостность склада остаются на стороне API/PostgreSQL; browser QA проверяет реальные жесты на клоне данных.
