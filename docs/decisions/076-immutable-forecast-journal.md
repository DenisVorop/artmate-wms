# ADR076. Неизменная история прогнозов и последующая проверка

Статус: принято. Дата: 2026-10-27.

## Задача

Пользователь хочет сохранять прогнозы в БД, сравнивать их с последующими продажами и уточнять новые расчёты по накопленной ошибке. Перезаписываемый `forecast_results/current` этого не обеспечивает.

## Решение

`forecast_journal` хранит опубликованные расчёты без срока удаления. Успешная публикация кэша и INSERT архива находятся в одной SQL-транзакции; input key является уникальным ID. Повторы не перезаписывают архив. Расчёт с устаревшим input key, отменённый worker или ошибка не создают опубликованную версию. GET никогда не создаёт архив и не запускает обучение.

Архив содержит будущие дневные количества операционного спроса (заказы за вычетом отмен), исходную кривую до поправки, фактически применённый коэффициент, временные границы, настройки, версию и стабильный состав алгоритмов. Каждая серия привязана к магазину, площадке, SKU, составу карточек и упаковке. Финансовые выкупы и возвраты не подменяют этот факт. Исторические графики за годы не копируются в каждый получасовой расчёт.

Сравнение читает сохранённый прогноз и текущие исправленные факты отдельно. Обновление API может уточнить факт, но не прежнее ожидание. Оцениваются только даты строго после дня публикации по Москве и не позднее последнего завершённого дня. Неизвестное не равно нулю. Дни отсутствия товара показаны, но исключены из ошибки скрытого спроса. MAE, WAPE и смещение относятся к одинаковому набору сопоставимых дней; при нулевом суммарном факте WAPE не определяется.

История доступна только руководителю: строгие DTO, allowlist AuthGuard, no-store, пагинация. Старые магазины и изменённые сопоставления/упаковки остаются в БД, но не смешиваются с активной конфигурацией. Web читает DTO через Swagger → Orval и runtime guards, UI-state — в forecasting/lib, read hooks — entities/forecast/model.

## Поправка по реальным ошибкам

Коэффициент проверяется отдельно для горизонтов 1–7 и 8–30 дней. Одна дата товара имеет один голос в своей группе горизонта, независимо от количества получасовых расчётов. Для обучения используется исходный прогноз, поэтому прежняя поправка не умножается повторно.

Нужны минимум 35 сопоставимых дат, достаточный объём и три последовательные недельные проверки. Для дальнего горизонта реально потребуется больше времени: обучающие даты и известные тогда версии фактов должны предшествовать публикации проверяемого прогноза. Поправка ограничена диапазоном 0,75–1,25, сглажена к единице и допускается при снижении MAE минимум на 5% и выигрыше минимум в двух из трёх проверок. Сценарии запуска/непроверенной сезонности исключены. Идентичность алгоритма — технический ключ состава моделей, а не человекочитаемое название.

Чтобы запоздалые факты и исправления отмен не проникали в прошлую обучающую выборку, архив дополнительно фиксирует известные на момент публикации факты по ранее прогнозировавшимся датам. Их объём ограничен рабочим окном. При проверке поправки версия факта должна присутствовать в таком снимке до публикации проверяемого прогноза. Отсутствие снимков означает ожидание данных, а не разрешение использовать будущее.

Для передачи в CPU-worker выбирается не более одной версии за каждый из последних 120 дней публикации. Это ограничивает стоимость расчёта поправки, но не удаляет архив. Сама проверка и применение коэффициента выполняются вне SQL lock и основного event loop. Сырьё, готовые остатки, ledger, задания и ключи интеграций не меняются.

## Ограничения

Старые расчёты, сохранённые только в перезаписываемом кэше до этого изменения, нельзя честно восстановить. История начинается с первой публикации после внедрения. Поправка не считается обученной в день включения: сначала накапливаются реальные последующие наблюдения.
