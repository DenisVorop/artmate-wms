# ADR 023: свободная очередь и подтверждённый цикл короба

Статус: принято, 2026-10-23.

## Контекст

Сборка должна поддерживать свободную очередь и плановое назначение, проверять исполнителя каждого скана и вести сотрудника от физической подготовки товара к готовому коробу. Прежний экран подставлял источник кнопкой, не требовал скана короба и закрывал каждый короб отдельным действием клиента. Канонический контракт: [design.md](../tasks/2026-10-23-assembly-flow/design.md).

## Решение

Сценарий находится в `features/assembly`: `lib` содержит RHF/Zod-схемы, фильтры очереди, доступность действий, определение текущего шага и интерпретацию результата серверной команды; `model` оборачивает типизированные shared-команды; `ui` разделён на очередь, рабочую панель, создание, назначение и поле текущего скана. API, включая `createdAt`, `boxCodeConfirmed` и обязательный `employeeId`, получен Orval из Nest Swagger. Никакой клиентский эффект не упаковывает короб и не захватывает следующее задание.

Очередь состоит из «Свободных», «Назначены / пауза», «В работе» и «Завершённых». Карточка показывает тематику, прогресс коробов и исполнителя. Выбор карточки — чтение, без команды захвата. Legacy `createdAt=null` сохраняется без выдуманной даты; сортировка по `(createdAt ?? '', id)` стабильна. После смены серверного статуса выбранная карточка остаётся открытой, даже если теперь относится к другому фильтру. Пользователь видит её новый раздел и может перейти к нему.

«Работаем как» — явный локальный выбор demo-исполнителя среди сотрудников на смене. Он не меняет назначение задания и не является авторизацией. Взять свободное либо своё ожидающее/приостановленное задание можно отдельной командой. Чужое назначение, другой активный task, отсутствие смены и завершённое задание объясняются рядом с недоступной кнопкой. Сервер остаётся источником проверок и разрешает гонку захвата.

При создании можно оставить свободную очередь или запланировать исполнителя, включая сотрудника вне смены. После создания назначение доступно в той же карточке, без вложенного диалога. Переназначить или снять назначение можно только между коробами в ожидающем/приостановленном задании: без учтённых единиц и без подтверждённого короба. В активном задании сначала нужна пауза; начатый короб нужно закончить. Несохранённый выбор руководителя не сбрасывается polling.

## Цикл одного короба

1. Сотрудник сканирует или вручную вводит код ожидаемой паллеты по FIFO. Код и адрес показаны для поиска, но никогда не подставляются в поле по кнопке.
2. Для нормы 20 показана физическая подсказка «Подготовьте 2 упаковки по 10 раскрасок». Для другой нормы — её фактическое количество. Упаковка и маркировка раскрасок физические; отдельного складского учёта пачек нет. Доступна печать этикетки текущего `openBoxCode` по существующему `/labels/box/{code}`.
3. После наклейки этикетки сотрудник сканирует код короба в изначально пустое поле. Неверный или старый код не открывает сканирование товара.
4. Каждая раскраска проходит по штрихкоду тематики. После подтверждения короба доступен явно описанный ручной режим: одно нажатие учитывает одну единицу, а не имитирует скан без записи.
5. Последний скан атомарно закрывает короб на сервере. Если места сборки нет, команда откатывается: остаётся N−1 и исходный ввод, пользователь готовит подходящее место и повторяет скан.

Каждый новый короб, включая следующий внутри одного задания, снова требует source scan, затем box scan. При смене партии внутри уже открытого короба подтверждается следующая паллета; подтверждение этого же короба сохраняется. Нормальный путь не показывает кнопку упаковки. Полный мигрированный короб с `boxCodeConfirmed=true` получает отдельный recovery-шаг и явный повторный ввод кода для `packTask`.

После серверного закрытия UI интерпретирует свежий snapshot: остаётся в текущем задании и показывает новый короб; либо выбирает уже активированное сервером следующее задание того же сотрудника с сообщением обоих кодов; либо показывает завершение и свободного сотрудника. UI не выбирает paused или чужие задания автоматически. Replay без прироста счётчиков называется подтверждением состояния и не сообщает о лишней единице или коробе.

## Правила взаимодействия

- `rule/cover-reachable-states`: предусмотрены пустые очередь/каталог/смена/место сборки, off-shift, чужой захват, пауза и неполный короб, legacy full, смена источника, серверный отказ, фоновая ошибка GET, автоматическое продолжение и завершение.
- `rule/preserve-user-input`: ошибка записи не очищает ввод. Поля сканов очищаются после успешной команды; смена poll snapshot не сбрасывает форму. Фоновый отказ Workspace сохраняет последнюю версию и открытое окно создания. Назначение сохраняет несохранённый выбор.
- `rule/no-nested-modals`: назначение редактируется внутри карточки, создание — один самостоятельный диалог.
- `rule/one-primary-action`: рабочая панель показывает один текущий этап; печать и ручное добавление имеют второстепенный приоритет. Закрытие обычного короба — результат последнего скана.
- `rule/name-object-scope-consequence`: явно разделены просмотр, захват, назначение, физическая подготовка и учёт единицы. Ручное добавление поясняет реальное изменение запаса.
- `rule/accessible-name-required`: поля имеют видимые подписи, у очереди и выбора исполнителя есть имена; состояние шагов — `aria-current`, прогресс — `progressbar`, запись — `aria-busy`, ошибки — `alert`, результат — `status`. Enter отправляет только текущий скан. На время записи переключение исполнителя и задания блокируется.

## Проверка и ограничения

`assembly-form.test.ts` проверяет свободное и назначенное создание, диапазон коробов, explicit null при снятии назначения и обязательный точный скан. `assembly-queue.test.ts` — фильтры, legacy-сортировку, поиск без мутации, ограничения захвата и назначения, цикл source→box→items, смену партии, новый короб и recovery. `assembly-transition.test.ts` — новый короб того же задания, переход только в серверное active-задание своего исполнителя, пустую/недоступную очередь и replay без ложного увеличения.

Физический сканер и принтер проверяются отдельно от браузерного прототипа. Отдельное мобильное приложение, настоящая авторизация и печать товарных этикеток не входят в этот этап. Этикетка короба остаётся тем же уникальным кодом при повторной печати.
