# 039. Локальные аккаунты и серверные сессии

Дата: 24.10.2026. Статус: принято.

## Хранение и первый вход

Схема 9 добавляет отдельные `auth_accounts`, `auth_sessions`, `auth_login_limits` и `auth_events`. Они не входят в `WorkspaceDto`, складские таблицы или сохранённые ответы команд. Миграция сохраняет все прежние сущности, ID, ревизию, количественный журнал и cached responses. Пароля по умолчанию и открытой регистрации нет.

Публичный `GET /api/auth/session` возвращает `needsSetup`, собственные `user`, `csrfToken`, `expiresAt` либо `null`. Первый аккаунт создаётся только через форму `setupAuth`: имя, уникальный логин и пароль. Запрос требует заранее разрешённого Origin, JSON и `X-WMS-Request: 1`. В одной SQL-транзакции проверяется отсутствие аккаунтов, создаётся новый сотрудник «Руководитель» со сменой `off` и первый manager. Создание сотрудника увеличивает складскую ревизию на один; миграция этого не делает. При конкурентном setup выигрывает ровно один запрос.

Логин нормализуется в lowercase, допустимы 3–64 символа `[a-z0-9._-]` с буквы или цифры. Новый пароль — 12–128 символов, без неявной обрезки пробелов. Сотрудник привязывается к аккаунту через неизменяемый `employeeId`; его рабочая должность `EmployeeDto.role` независима от прав `manager`/`employee`. Удаления сотрудников, аккаунтов и истории нет.

## Пароли и сессии

Используется асинхронный Node.js `scrypt`: `N=32768`, `r=8`, `p=3`, случайная соль 128 бит, производный ключ 256 бит, `maxmem=64 MiB`. Сравнение ключей — `timingSafeEqual`. Для неизвестного логина выполняется такая же проверка dummy-хеша. Ошибки входа не раскрывают, существует ли логин и заблокирован ли он. Пароли, хеши и session tokens не выводятся в API-ответах и журнале приложения. Параметры соответствуют одному из вариантов [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt); вызов и лимит памяти проверены по [Node.js crypto.scrypt](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).

Сессия действует 12 часов без автоматического продления. Случайный непрозрачный токен имеет 256 бит, передаётся клиенту только в cookie `wms_session` (`HttpOnly; SameSite=Strict; Path=/`). В SQL хранится только SHA-256 токена. Имя задаётся `WMS_AUTH_COOKIE_NAME`, чтобы preview мог использовать отдельную cookie. Для локального HTTP Secure выключен; при HTTPS необходимо задать `WMS_AUTH_COOKIE_SECURE=true`.

CSRF-токен отдельный, случайный, выдаётся только собственным `auth/session` и меняется при новой сессии. На аутентифицированных записях обязательны точный разрешённый Origin и `X-WMS-CSRF`. `WEB_ORIGIN` — полный статический список через запятую; он не выводится из Host или forwarded headers. Значения по умолчанию — loopback/localhost с портами 3080/3081. Login/setup дополнительно требуют `X-WMS-Request: 1`, поскольку сессии ещё нет. Ответы API имеют `no-store`, `nosniff`, запрет встраивания и ограниченный referrer.

Login ограничен SQL-счётчиками до дорогой проверки пароля: пять попыток на логин и 30 на непосредственный IP за 15 минут. Forwarded headers не считаются источником IP. Успех очищает счётчик логина, но не IP. Таблица ограничена 10000 ключами, старые окна удаляются. Ограничения и сессии сохраняются после перезапуска.

## Управление аккаунтами

Менеджер получает `AuthAccountsDto {items}` и может создать аккаунт существующему сотруднику, изменить роль/блокировку, сбросить пароль или отозвать сессии. Выдаваемый менеджером пароль временный: до личной смены доступны только собственная сессия, выход и смена пароля. Последнего включённого manager нельзя заблокировать или понизить. Сброс собственного пароля менеджером отклоняется: для этого есть смена с проверкой текущего.

Смена пароля отзывает все прежние сессии и создаёт новую с другой cookie и CSRF. Изменение роли/блокировки, сброс пароля и ручной отзыв также отзывают сессии. Самоотзыв и допустимое самопонижение очищают cookie. Роль, статус аккаунта и срок сессии читаются из SQL заново на каждом запросе.

Успешные входы, выходы, смены пароля и административные действия записываются в `auth_events`: вид, время, автор и целевой аккаунт. Пароли, токены и полные тела форм туда не попадают. Восстановление забытого пароля последнего manager без второго manager пока не имеет публичного сценария; промышленный recovery/MFA/SSO — отдельный этап.

## Проверка

`auth.test.ts` использует настоящий Nest HTTP, cookie и headers: bootstrap race, 401/403, Origin/CSRF, временный пароль, ротацию, смену роли/блокировку/reset/revoke, отзыв между guard и replay, сохранение сессии и throttle после restart, полный складской цикл сотрудника. `auth-migration.test.ts` проверяет schema8→9 и повторный запуск без изменения прежнего склада, журнала и cached responses.

`WMS_AUTH_TEST_DATABASE_URL` разрешён только для новой отдельной базы с суффиксом `_test`. Полный прежний набор использует другую `WMS_TEST_DATABASE_URL`. Рабочая и preview-базы запрещены для тестов.
