# ADR-041 — интерфейс доступа и изоляция пользователей

Дата: 24 октября 2026. Статус: принято.

## Слои

`entities/session` содержит SessionProvider/useSession и очищенный публичный снимок сессии. Реальный CSRF остаётся в module-memory shared API, поле csrfToken контекста всегда null; пароли и cookie token не сохраняются в QueryClient, localStorage или sessionStorage. `features/auth` отвечает за первый запуск, вход, обязательную смену временного пароля и меню собственной сессии. `features/access-management` управляет доступом существующих сотрудников. `_pages/team-screen` соединяет управление командой и доступом, без feature-to-feature импорта. Все страницы, включая этикетки, находятся под общей AuthBoundary в AppProviders.

Роль определяется серверным ответом, а не свободным полем должности сотрудника. Worker навигация ограничена рабочими экранами; прямая ссылка на управленческий раздел показывает отказ и путь к своим заданиям. Конструктор недоступен, навигация/масштаб карты сохраняются. Исполнитель реальных операций фиксирован по вошедшей учётной записи, выбор другого человека оставлен только назначению руководителем. Удерживаемые чужими работами адреса отображаются обезличенными.

## Первый запуск и действия с доступом

Сначала форма первого руководителя; после создания доступен обычный вход. Новая учётная запись сотрудника/сброс получает временный пароль и обязательную замену до допуска к складу. Текущий пароль можно изменить в своём профиле. Самосброс из карточки аккаунта недоступен с пояснением. Две роли видны одновременно. Защита последнего руководителя отражена в UI и повторяется сервером.

Блокировка и разрешение входа обратимы; подпись объясняет отзыв сеансов и сохранение заданий/резервов. Отзыв всех сеансов подтверждается с именем/логином и масштабом действия. Создание и сброс не выводят пароль для повторного просмотра и не отправляют сообщений сотрудникам; пароль передаёт руководитель лично. Формы сохраняют ввод при ошибках и допускают автозаполнение/вставку.

## Изоляция и асинхронные гонки

Изменение user ID/роли/mustChangePassword, выход или потеря сессии увеличивают auth epoch, отменяют чтения, очищают QueryClient и реестр незавершённых команд старой личности. Безопасная metadata владельца в sessionStorage содержит только публичные id/роль: same-user reload может продолжить idempotent retry, другой пользователь не наследует его. Auth POST вообще не проходит через складской replay и не сохраняет credential payload.

Одной проверки epoch в transport недостаточно: команда после HTTP-ответа может ожидать отмену polling/свежий snapshot. Поэтому command bridge проверяет scope после каждого await, перед сравнением ревизий, записью кэша и fallback. Потеря scope не проглатывается как ошибка обычного обновления. Старый ответ руководителя с большей revision не может перетереть новую проекцию сотрудника. Session fetch также упорядочен serial/intent и не усыновляет ответы предыдущего login/logout намерения.

Поддерево склада имеет key user.id/role/mustChangePassword; при смене личности оно перемонтируется, закрывая старые формы и режимы конструктора. HTTP401/403 инициируют перепроверку сессии; сетевой отказ показывает восстановление связи, а сервер остаётся источником допуска каждой мутации.

## Проверки

Тесты проверяют формы, sanitized session shape, owner scope и purge registry, отсутствие auth retry/credential persistence, transport epoch и гонки command bridge во время cancelRead/readCurrent/invalidate. Отдельные тесты охватывают навигацию worker и подсказки резервов. API права проверяются независимо через настоящий HTTP и PostgreSQL.
