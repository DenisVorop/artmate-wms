# 048. Инвентаризация на рабочем экране сотрудника

Статус: принято. Дата: 2026-10-24.

## Сценарий

`EmployeeStocktakes` экспортируется из существующего feature stocktakes с props `initialDocumentId?`, `onIdle`, `onProblem?`. Экран руководителя `StocktakesFeature` и его права не меняются. Сотрудник видит карточки собственных документов counting/review и свободные queued, явно берёт документ и считает одну ячейку за раз. Ожидающие утверждения документы доступны как статус, без управленческих diff/approve/cancel/create и общей таблицы истории.

После успешного сохранения выбирается следующая непересчитанная ячейка; устаревшая ячейка требует пересчёта. Доступные адреса имеют приоритет перед занятыми, но занятые не исчезают: видны серверные причины и путь восстановления. Свежие сохранённые ячейки можно открыть через компактный выбор адреса. Когда все ячейки подсчитаны, основное действие — передать документ руководителю на проверку. Неизвестные коды остаются расхождениями для руководителя; ошибочный ввод можно исправить повторным подсчётом.

## Фактический ввод

Compact-режим существующего CountLocationForm начинает новый подсчёт с пустыми фактическими кодами адреса, паллет и коробов. Коды товара из baseline не подставляются в факт, список ожидаемых коробов не превращается в чеклист подтверждения. Известные сохранённые наблюдения могут открываться повторно. Количество не выводится из ожиданий: пустое значение не означает 0. Found/present=false исключает паллету из наблюдения, present=true с quantity=0 сохраняет факт физической пустой паллеты. Осмотр ячейки подтверждается отдельным обязательным флажком, включая пустой адрес.

## Защита данных

Используются существующие useStocktakeCommands, generated Orval DTO, requestId/replay transport, auth epoch и монотонный выбор свежей revision. Компонент не создаёт отдельный HTTP-клиент и не рассчитывает складские исправления. Mutation возвращает актуальный документ; polling не сбрасывает dirty-форму.

Переход к другой ячейке, документу или рабочему экрану при несохранённом вводе требует явного решения: остаться либо перейти с очисткой локального ввода. Server baseline/count change блокирует старую форму до явного восстановления. Refresh с сохранённым результатом или dirty-вводом использует существующее предупреждение о сбросе одной строки и сохранении её истории. Только руководитель утверждает изменение остатков на прежнем экране.

## Проверка

Focused stocktake tests покрывают порядок карточек, исключение чужих/архивных документов, переходы между ячейками, stale/busy recovery, dirty navigation, пустые фактические коды и различие отсутствующей/пустой паллеты. Общие формы и команды проверяются существующими тестами stocktakes. Backend read-only audit подтверждает необходимость показывать сотруднику сначала собственный товар в пути; API не меняется в этом этапе.
