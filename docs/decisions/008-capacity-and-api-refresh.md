# ADR-008 — физическая вместимость и обновление состояния клиента

Дата: 23 октября 2026 года.

## Размеры и масса

Приёмка вводит высоту, ширину и глубину паллеты вместе с поддоном. Масса может быть неизвестна, но неизвестное значение не равно нулю: место с обязательным весовым ограничением требует известной массы. Габариты API — целые миллиметры; форма приёмки показывает сантиметры.

В Остатках доступны профили упаковки каждого SKU: габариты короба/поддона, коробов в слое, предел слоёв и массы. Сервер проверяет прямоугольную схему слоя. Вместимость конкретного адреса ограничена одновременно профилем, габаритами, высотой, массой и лимитом коробов. Значения миграции — демонстрационные и требуют обмера.

Закрытые короба и готовые паллеты сохраняют снимок упаковки. Профиль не меняет их задним числом; при незавершённом задании изменение профиля блокируется.

## Путь размещения

Нулевая паллета остаётся физически на адресе до подтверждения вывоза. Во время переноса у паллеты и дочерних коробов нет фиктивного адреса: состояние in_transit, ответственный и плановая цель видны явно. Возвратный резерв не называется свободным местом.

## Синхронизация API

Идемпотентный ответ может отражать прежнее состояние и старую версию схемы. После успешной команды общий API-адаптер запрашивает свежий getWorkspace через generated SDK, вместо присвоения ответа старой команды как текущего состояния. FSD не меняется: API-адаптер не принимает складские решения, feature model вызывает команды, backend валидирует правила.

Все новые типы и функции получены из NestJS Swagger через Orval. Общего пакета контрактов нет.

### Подтверждённая запись и сбой обновления

Успех команды и успех последующего чтения разделены. После подтверждённой записи сбой GET не возвращается форме как ошибка сохранения: иначе повторное нажатие с новым requestId могло бы продублировать приёмку или отгрузку. Оркестрация вынесена в pure helper `shared/api/run-warehouse-command.ts` и проверена через fake client без сети и мутации настоящего склада.

Перед отправкой требуется загруженный snapshot текущей схемы. После записи адаптер повторно отменяет возможное фоновое чтение и запрашивает свежий snapshot. При сбое чтения использует ответ команды только при наличии всех массивов текущей схемы, включая sections и movements. Исторический v1 replay не перезаписывает кэш: callback получает актуальный доступный v2 cache или загруженный до команды v2 snapshot. Кэш помечается устаревшим для восстановления polling. Неудача собственно команды по-прежнему отображается как ошибка сохранения.

В списке коробов состояние физического перемещения определяется по родительской паллете. Нулевой адрес во время переноса показывается как «В пути / В перемещении», а не как «На складе». Исторический отгруженный короб сохраняет статус отгрузки независимо от дальнейших перемещений остатка паллеты.

### Потерянный ответ самой команды

Общий транспорт хранит в sessionStorage только технический реестр неподтверждённых операций: SHA-256 от метода, URL и канонического JSON тела без requestId → исходный requestId. Поля товара, количества и тело команды в хранилище не записываются. Перед POST ключ обязательно сохраняется; при недоступном хранилище запись не отправляется.

При ручном повторе того же payload используется прежний requestId, включая перезагрузку страницы в той же вкладке. Подтверждённый валидный ответ и окончательный 4xx удаляют запись. Сетевая ошибка, 5xx, неоднозначный timeout 408 и некорректный 2xx сохраняют ключ. Успешный следующий одинаковый скан является новой командой с новым requestId. Одновременные одинаковые команды в одной вкладке отклоняются с понятным сообщением, а не объединяются с потерей единиц.

Канонизируется также отправляемое JSON тело, включая порядок вложенных полей: серверный fingerprint использует JSON.stringify. Валидность командного ответа проверяется по форме snapshot; legacy replay допускается, но не перезаписывает v2 кэш. GET остаётся прежним. Автоматических повторов POST нет. После закрытия вкладки sessionStorage исчезает; промышленная офлайн-очередь операций с отдельным восстановлением намерений в этот этап не входит.

Тесты воспроизводят commit с потерей ответа и проверяют, что повтор использует тот же серверный ключ и не создаёт вторую запись. Дополнительно проверены новый ключ после успеха, изменение после 4xx, 5xx, некорректный JSON/2xx, отказ хранилища до записи, ошибка очистки, конкурентный одинаковый запрос и неизменённый GET.
