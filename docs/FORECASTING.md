# Прогнозирование спроса

Архитектура и инварианты: [ADR068](decisions/068-seasonal-demand-forecasting.md). Подробный план и ход работы: [задача](tasks/2026-10-26-seasonal-forecast/task.md).

Как читать: незавершённая страница не попадает в обучение. Загрузка истории не двигает складской товар. Только последнее действие руководителя может создать складское задание.

## Интерфейс

На странице «План сборки» раздел «Прогноз и история» содержит прогресс архива, выбор тематики, график факта/прогноза, сравнение моделей и минимум коробов. Для WB отдельно подключается финансовый readonly ключ того же продавца. Исходный ключ поставок остаётся действующим. Начальную дату можно выбрать в пределах доступности API; «с начала торговли» означает последовательную проверку месяцев, а не выдуманную историю до первой продажи.

Разные метрики показаны отдельными источниками. Выкупы WB и заказы Ozon нельзя непосредственно складывать как один ряд продаж. Неизвестные дни рисуются пропусками; достоверные нули сохраняются. Товарные соответствия применяются в складских единицах один раз.

## Модели и качество

Средний спрос — безопасная исходная модель. Годовая сезонность использует повторение календарного периода; вариант с ростом корректирует прошлый год по недавнему сопоставимому периоду. Ridge использует небольшой фиксированный набор сезонных признаков и тренд, без внешнего сервиса и передачи данных.

Проверка на прошлом отрезает будущие наблюдения для каждого обучения. Сравниваются ошибка в штуках, относительная ошибка и смещение. Сложная модель допускается только при достаточной истории и устойчивом улучшении минимум на 5%, включая рабочий горизонт. Два года истории не гарантируют ни преимущество, ни высокую уверенность. Промоакции и внешние изменения не известны модели заранее.

Поставки и остатки не вычитаются внутри моделей повторно: прогноз оценивает будущую потребность, а существующий план рассчитывает объём дополнительной сборки. Исторические остатки, которых API не дал, не восстанавливаются задним числом как известные.

## Эксплуатация

MarketplaceScheduler обновляет текущие данные каждые 30 минут. HistoryScheduler продолжает разрешённые задания, уступая текущему импорту. ForecastScheduler проверяет входную версию каждую минуту и пересчитывает только при изменении. Все запускаются только в main после listen и прерываются при shutdown. Тяжёлые вычисления выполняются вне SQL lock и API event loop.

При смене магазина архив прежнего аккаунта сохраняется, но не применяется к новому. Переподключение финансового WB ключа требует совпадения seller SID. Ответ внешнего API после отзыва прав или изменения подключения не публикуется.
