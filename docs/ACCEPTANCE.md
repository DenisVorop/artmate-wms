# Приёмка, пилот и восстановление

Это план будущих проверок, не отчёт об уже выполненных тестах приложения. Результаты заполняются во время реализации и пилота. Документация сама по себе не доказывает корректность WMS.

## 1. Контрольный набор данных

Создать в тестовом окружении:

- SKU A — «Котики-2», SKU B — другая тематика; разные товарные штрихкоды.
- Упаковку A-v1: 20 раскрасок в коробе; размеры измерены.
- Старую партию L1 и новую L2 с устойчивым порядком FIFO.
- Входящую паллету P1 с 10 единицами L1 и P2 со 100 единицами L2.
- Отдельный сценарий P3 с 1000 единицами одной партии.
- Ячейку LOW с полезной высотой 1 метр и высокую паллету 2 метра.
- Адрес готовой продукции вместимостью 18 коробов по проверенной укладке.
- Адрес приёмки, станцию НЗП, готовую сборку, зону отбора с доступом с четырёх сторон, зону отгрузки и карантин.
- Двух сотрудников сборки, приёмщика, отгрузчика и руководителя; часть ролей можно назначить одному человеку.
- Два устройства для конкурентных действий.

Проверки запускаются на изолированных данных. При повторе идентификаторы и состояния должны быть известны; нельзя зависеть от случайных остатков прошлого прогона.

## 4. FIFO и доступность

| ID | Действие | Ожидаемый результат |
|---|---|---|
| FIFO-01 | Создать задание при доступных L1 и L2 | Сначала резервируется доступный остаток L1 |
| FIFO-02 | Два сотрудника запрашивают последние 10 единиц L1 | Совокупный резерв не больше 10; остаток потребности уходит в L2 либо ожидание |
| FIFO-03 | Старый товар заблокирован | Он не выдаётся в обычную работу; причина видна, обход не скрывается |
| FIFO-04 | Старый короб на верхнем ярусе, паллету можно спустить | Создаётся предварительный спуск, а не автоматический выбор новой партии |
| FIFO-05 | Есть чистый L1, смешанный L1/L2, чистый L2 | Очередь соответствует выбранному правилу: чистый L1 → смешанный → чистый L2 |
| FIFO-06 | Выбрать новую партию вместо доступной старой | Отклонение запрещено обычному сотруднику; разрешённое содержит причину и автора |
| FIFO-07 | Нижний короб старой партии перекрыт новой партией после спуска | Проблема доступа видна; мягкий порядок внутри партии не разрешает незаметный переход к новой партии |
| FIFO-08 | У старого запаса неизвестна фактическая дата | Происхождение явно неизвестно; порядок задаётся отдельным согласованным правилом |
| FIFO-09 | Даты производства и поступления дают разный порядок партий | Используется порядок поступления на склад |
| FIFO-10 | Ранний короб перекрыт, доступен поздний короб той же партии | Допустим доступный короб без обязательного перекладывания и отдельного разрешения |
| FIFO-11 | Старой партии не хватает, она дополнена новой того же SKU | Разрешённое смешение сохраняет происхождение и основание, SKU паллеты остаётся единственным |

## 10. Автоматические проверки сохранения количества

После каждого сквозного сценария запускать сверку:

1. Приход + начальные остатки + возвраты − отправки − утверждённые списания = текущий физический учётный запас.
2. Текущий запас = raw + wip + finished + quarantine без повторного добавления содержимого паллет.
3. Сумма состава каждого закрытого короба равна количеству в его товарных балансах.
4. Сумма активных резервов не превышает допустимый запас с учётом потреблённой части.
5. Занятость и активный резерв места не превышают проверенную вместимость.
6. У каждого контейнера один текущий путь расположения или явное ответственное перемещение.
7. Ни на одной паллете нет нескольких SKU.
8. У каждой принятой команды есть ровно один результат; у повторной доставки нет новой операции.
9. У отгруженного короба нет активного остатка склада и активного резерва другой отгрузки.
10. У каждой корректировки/обхода FIFO есть основание и автор.

Эти проверки должны работать по реальной БД. Моки API не доказывают отсутствие гонок резервирования.

## 11. Нагрузка и удобство

Проверить на согласованном количестве одновременных сотрудников и объёме адресов/коробов. Зафиксировать p50/p95 задержки сканирования, скорость обновления карты, число ошибок и время восстановления соединения.

Серия реальной сборки должна включать повторяющиеся одинаковые штрихкоды, смену партии, перенос телефона, блокировку экрана и замену этикетки. Измерять полный цикл короба: набор, сканирование, упаковка, размещение. Изолированная скорость чтения штрихкода не равна производительности сборки.

Проверить мобильный экран без горизонтальной прокрутки, крупные действия, фокус сканера, текст ошибок, доступность информации без цвета, клавиатурный выбор в административной части.

## 12. Восстановление

RPO — допустимая потеря последних данных по времени. RTO — допустимое время восстановления работы. Значения выбираются владельцем с учётом процесса склада и проверяются восстановлением.

1. Сделать резервную копию тестовой рабочей БД с НЗП, смешанным коробом, активным резервом и незавершённым спуском.
2. Восстановить её на отдельную базу, не поверх действующей.
3. Проверить миграции и отсутствие повторного исполнения старых команд.
4. Выполнить сверку количеств, составов, мест и резервов.
5. Открыть смену с другого устройства и продолжить незавершённые процессы.
6. Измерить фактические потери данных и время восстановления.
7. Сравнить результат с согласованными RPO/RTO; скорректировать резервирование и процедуру, если цели не достигнуты.

Откат версии приложения не должен автоматически откатывать складские операции, которые уже физически произошли. Для несовместимой миграции нужен отдельный проверенный порядок восстановления.

## 13. Регламент сбоя на складе

- При неопределённом ответе остановить текущую операцию и сохранить физический контейнер на известном месте.
- Проверить состояние команды по ID и серверный счётчик.
- При продолжительном простое руководитель включает согласованный аварийный режим: маркирует затронутые контейнеры и ведёт последовательный журнал фактических действий.
- После восстановления внести/сверить аварийные движения через утверждённые операции, пересчитать НЗП и затронутые паллеты.
- Возобновить обычную работу после подтверждения согласованности; не вводить те же движения одновременно как приёмку и корректировку.

Конкретный допустимый объём аварийной работы определить в пилоте. Полноценный автономный режим клиента в первую версию не входит.

## 14. Условия промышленного запуска

1. Пройден полный цикл на реальном устройстве и промаркированных адресах.
2. Проверены смешанные партии, пауза, передача, спуск и возврат паллеты.
3. Нет нерешённых ошибок двойного учёта, потери партий и двойного списания.
4. Начальные остатки пересчитаны; неизвестное происхождение обозначено честно.
5. Обязательные права и причины корректировок настроены.
6. Выполнено восстановление из резервной копии.
7. Сотрудники знают штатный процесс и действия при потере сети.
8. Замерены фактические показатели пилота и определён порядок расширения.
9. Выбран один источник складского учёта для включённых в WMS товаров.
10. Есть ответственный за поддержку и порядок внесения обновлений.

## 15. Запись результатов

Для каждой проверки при реализации записывать: ID, дата, версия приложения/схемы, окружение, устройство, исполнитель, фактический результат, ссылка на дефект при провале, повторная проверка после исправления.

До появления приложения ни одна проверка из этой матрицы не считается пройденной. Статус этапов находится только в IMPLEMENTATION_PLAN.md.
